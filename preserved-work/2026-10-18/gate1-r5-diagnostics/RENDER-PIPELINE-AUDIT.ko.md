# Gate 1 R5 — 동일 카메라 렌더 전달 진단

대상: `37583421daba9a0e127c208f9c6d41e488a76b5c`, `redesign/folded-playhouse-gate1-20261017`.

이번 산출물은 현재 실패 원인을 확인하기 위한 진단입니다. 새 디자인이나 승인 완료본이 아닙니다. 제품 코드·모델·베이크를 변경하지 않았으며, 모든 진단 파일을 프로젝트 소스 밖에 저장했습니다. Gate 1은 불합격 상태이며 Gate 2, 새 인트로 영상 제작, 푸시·배포는 진행하지 않았습니다.

## 비교 조건과 한계

- Blender: 현재 R4 최종 `.blend`, Cycles CPU 128 samples, 1920×1080. 이 Blender 빌드는 OpenImageDenoise를 지원하지 않아 디노이징 없이 렌더했습니다. 정상 진행 중인 베이크를 중단하거나 중복 실행하지 않았습니다.
- Web: 해당 커밋의 `createFoldedWorld`를 그대로 가져오는 별도 진단 화면. Chromium/Playwright, 1920×1080, DPR 1, progress=0, entrance=1, pointer=(0,0). 웹GL은 실제로 확인된 SwiftShader입니다. 하드웨어 GPU 성능으로 해석하지 않습니다.
- 두 카메라: 위치 (0,0.3,11.7), 목표 (0.3,-0.05,0), 수직 FOV 38°, 화면비 16:9. Blender 축 변환은 (x,y,z)→(x,-z,y)입니다.
- 원본 커플 RGBA를 양쪽 동일 위치·크기로 사용했습니다. Blender에서는 원래 베이크용 회색 가림판이었던 평면에 카메라/반사 광선용 원본 이미지 방출 재질을 임시로 연결했습니다. GI 계산용 원래 가림판은 보존했습니다. `.blend`를 저장하지 않았습니다. 웹의 인물은 `toneMapped=false`, Blender 인물은 AgX를 통과하므로 인물 색을 재질 전달의 기준으로 삼지 않습니다.
- Blender/Three 투영 행렬의 최대 차이는 약 3.11×10⁻⁷, 축 변환한 카메라 world 행렬 차이는 약 2.91×10⁻⁷로 일치합니다.
- 영상 텍스처는 이 진단 첫 프레임에서 readyState=1로 기록됐습니다. 움직이는 영상의 디코딩·통합 검증으로 사용하지 않습니다.
- 3D 비교에서는 DOM 문구를 제외했습니다. 문구 충돌은 별도의 실제 페이지 캡처로 확인합니다.
- Blender AgX와 Three ACES는 서로 다른 디스플레이 변환입니다. 따라서 원본 비교를 픽셀 동일성 시험으로 부르지 않습니다. AgX/Standard 및 웹 AgX 진단 변형도 함께 제공합니다.
- Blender의 경로 추적 반사와 웹의 평면 반사·거칠기 블러는 다른 경로입니다. 평면 반사 화면이 원본의 정확한 PBR 전달이라는 주장은 하지 않습니다.

## 확인된 전달 불일치

### 1. 베이크의 물리량과 Three 라이트맵 입력

현재 베이크는 DIFFUSE, DIRECT+INDIRECT, COLOR 제외입니다. 저장 시 RGB를 3으로 나누고 웹에서 `lightMapIntensity=3`으로 복원합니다. 그러나 Three r186의 `lights_fragment_maps.glsl.js`는 이 값을 입사 irradiance에 더하고 `BRDF_Lambert`에서 π로 나눕니다.

수치 보정 실험은 조명·환경 없이 선형 albedo=0.5인 Lambert 평면과 값 1인 선형 float 라이트맵을 사용합니다. Three 실제 readback은 intensity=1에서 RGB 0.1591549367, intensity=π에서 RGB 0.5였습니다. WebGL 오류는 0입니다. Blender 실측은 원본 선형 렌더 RGB=(0.5,0.5,0.5), color-excluded bake RGB=(1,1,1), 원본/(albedo×bake)=1입니다. 즉 현재 저장 복원 3 외에 π 변환이 필요하다는 점이 두 엔진의 독립 실험으로 확인됐습니다. 이 보정은 Lambert 규약 검증이며, Principled/Physical BRDF의 에너지 보존 차이까지 자동 해결한다는 뜻은 아닙니다.

### 2. 조명과 환경을 그대로 전달하지 않음

Blender 원본은 면광원 5개와 낮은 청회색 World입니다. 웹은 다른 위치·강도·색의 면광원 2개, 방향광 1개, stock RoomEnvironment를 추가합니다. 이미 직접광까지 베이크된 diffuse 위에 별도 diffuse 조명을 더하므로 방향성과 명암비가 원본과 달라집니다. 금속 반사 환경도 원본 공간과 다릅니다. Blender W와 Three의 광학 단위를 이름만 보고 1:1로 대입하면 안 됩니다.

### 3. 재질의 일부만 glTF에 전달됨

baseColorFactor·roughness·metalness는 전달되지만 Blender procedural Noise/Bump는 glTF로 나오지 않습니다. 웹은 따로 만든 normal PNG를 UV에 65×65 또는 80×30 반복해 넣습니다. 따라서 원본 미세 표면의 동일 전달이 아닙니다. 원본 표면 법선의 전용 tangent-space bake와 UV 계약이 필요합니다.

### 4. 톤매핑과 색 관리

원본 AgX exposure=0과 웹 ACES exposure=1(Three의 승수)은 서로 같은 규약이 아닙니다. exposure 숫자도 직접 비교할 수 없습니다. 선형 베이크 PNG를 NoColorSpace로 읽는 방향 자체는 맞습니다. 런타임 PNG8 양자화 및 약한 노이즈 완화는 별도 오차 요인입니다.

알코브 라이트맵의 red 최대는 약 0.616이고 0.995 초과 비율은 0입니다. 따라서 알코브 전체의 평평한 인상을 광범위한 PNG 포화로 설명할 수 없습니다. room 지도 일부만 약 0.124%가 이 범위입니다.

### 5. UV와 공유 재질 계약

현재 glTF는 TEXCOORD_0만 있고 웹 라이트맵은 channel=0입니다. Three r186은 이 구성을 지원하므로 UV2가 없다는 사실만으로 오류라고 판단하지 않습니다. UV0를 UV1에 복제하고 channel=1로 바꾼 실제 캡처 2,073,600픽셀을 비교한 결과 최대 채널 오차 0, 다른 픽셀 0으로 완전히 같았습니다. UV2 부재는 이번 실패 원인이 아닙니다.

실제 메타데이터에서는 Architecture의 `Cube002_5`와 별도 `Passage_Warm_Rim`이 같은 `Warm_IntegratedLight.001` UUID를 공유하며, 둘 모두 room-irradiance.png가 붙어 있습니다. 별도 곡선에서 변환한 띠에도 UV는 있지만 이 UV는 room atlas에 베이크된 좌표가 아닙니다. 따라서 수신자에서 넣은 라이트맵이 다른 메시까지 따라가는 공유 재질 누출이 확인됐습니다. 수정 시에는 라이트맵 수신 계약별로 재질을 분리해야 합니다.

### 6. 최종 모델과 베이크 시점이 다름

베이크 후 패시지 발광 띠와 카운터 아래쪽 재질이 수정됐습니다. 수정 뒤의 `.blend` 네이티브 렌더와 기존 베이크는 완전히 같은 상태가 아닙니다. 모델·재질·조명·베이크 입력의 해시를 묶어 최종 export 전 상태를 고정하는 절차가 필요합니다.

## 원본 자체의 아트 디렉션 판정

Blender 원본 AgX 이미지를 직접 확인했습니다. 인물의 존재감과 원본의 벽/바닥 음영은 보이지만, 큰 정면 원형 니치와 금속 테두리가 독립된 액자처럼 읽힙니다. 카운터는 앞면이 크고 모서리가 직각에 가까운 상자 형태이며, 위쪽 캐노피/왼쪽 벽 접합의 꺾임도 원본에서 확인됩니다. 따라서 이 세 문제는 웹 렌더 전달만 고쳐 해결할 수 없습니다. 원본 자체의 곡면·단면·카메라에 대한 재설계가 필요합니다.

화면 왼쪽 통로의 커튼과 밝은 작은 가구, 빈 후방 벽도 원본에 존재합니다. 추가 소품으로 가리는 방법보다 문구 안전 구역과 통로의 공간 배치, 목적지의 의미 있는 중심을 먼저 설계해야 합니다. 원본 렌더를 합격작으로 제출하는 것이 아닙니다.

## 웹 비교의 직접 판정

현재 웹은 원본보다 왼쪽 벽의 광량 구배가 약하고, 카운터/니치의 음영과 바닥 반사가 다른 방식으로 표현됩니다. AgX만 바꾼 이미지에서도 원형 프레임과 상자 문제는 그대로입니다. runtime lights/env/normal/반사 overlay를 끄고 bake에 3π를 적용한 진단에서는 원본 방향의 음영이 더 잘 드러나지만 금속 반사와 원본 법선·색 관리가 모두 복원된 완성안은 아닙니다. 이 변형은 원인 분리용일 뿐 제품에 적용하지 않았습니다.

## 수정 순서 — 모델 추가에 앞선 조건

1. 같은 카메라의 원본/웹 비교와 선형 보정 결과를 먼저 검토합니다. 큰 원형 프레임·상자형 카운터·꺾인 윤곽이 원본에도 있으면 전달 버그만 탓하지 않습니다.
2. 베이크 저장량→Three irradiance 변환을 명시하고 중복 diffuse 광을 분리합니다. 금속·반사 조명은 별도 환경 계약으로 유지합니다. 단순히 밝기만 올려 합격 처리하지 않습니다.
3. UV/공유 재질/색 관리/법선 전달을 독립적으로 검증합니다. 모프 전후에도 라이트맵이 늘어나는 한계와 동적 접촉 그림자를 확인합니다.
4. 원본 자체가 부족한 부분은 실제 곡면의 연속성과 실루엣, 카운터 단면, 비대칭 벽 니치로 재설계합니다. 문구 안전 영역을 먼저 고정하고 통로는 그 오른쪽 깊이에 배치합니다. 인물을 압도하는 원형 장식을 추가하지 않습니다.
5. 다음 공간의 중심은 두 사람과 연결되는 빛·미디어 조형물과 깊이 있는 선물 공간으로 설계합니다. 무의미한 의자 두 개로 채우지 않습니다. Gate 2 스토리 구현과는 구분합니다.
6. 고정 구도 품질을 먼저 재검수합니다. 이후 동일 오브젝트의 실제 모프·포인터·진입·역복귀를 다시 검증합니다. 품질 통과 전 새 인트로 렌더를 제작하지 않습니다.

## 보존과 승인

게임·API·라우트·갤러리·편지·건의사항·한국어/스페인어 파일은 이번 진단에서 수정하지 않았습니다. 별도 게임 작업은 건드리지 않았습니다. 원본 .blend와 현재 커밋을 보존했습니다. 현재 자료는 실패 원인 검토용이며 다음 구현 방향에 대한 총괄 검수 대기 상태입니다. Gate 1 사용자 승인은 별도로 필요합니다.

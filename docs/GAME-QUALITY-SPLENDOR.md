## 비교의 범위와 현재 기반

비교 대상 후보는 Board Game Arena의 Splendor(https://boardgamearena.com/gamepanel?game=splendor)와 원 출판사 Space Cowboys(https://www.spacecowboys.fr/splendor-en)다. 공식 페이지에 읽기 전용 접근을 시도했지만 세션 프록시가 둘 모두 `Tunnel connection failed: 403 Forbidden`으로 차단했다. 따라서 최신 경쟁사 화면·현재 기능·직접 플레이 결과를 검증했다고 주장하지 않는다. 아래는 현재 소스와 저장소의 기존 시각 감사에 근거한 구체적인 제품 개선안이다.

현재 원본 90장 개발 카드·10장 귀족 아트, canonical 매핑, 2인 규칙, 예약/금 토큰/10개 제한/귀족 선택/15점 동수 턴 종료가 이미 있다. `TableGames.tsx`에는 확정 스냅샷 기반 카드 도착·구매·귀족·보석 이동 모션과 reduced-motion 대응이 있다. `audio.ts`에는 스플렌더 전용 선택·구매·예약·귀족·차례·승리 합성 효과음이 있다. 이것을 새로 추가해야 할 기능으로 분류하지 않는다.

기존 감사(`docs/QUALITY-VISUAL-AUDIT.json` splendor 항목)는 KO 1440×900 보드 높이1546px, ES 1920×1080 1399px를 기록한다. 아래 tier와 내 토큰이 두 화면 모두 화면 아래에 있다. 이 기록은 초기 상태 캡처이며 이번 세션 실제 플레이 측정값이 아니다. 문서상 기존326테스트와 빌드 통과도 상용 품질 승인 증거는 아니다.

## 1. P0 — 시장·은행·내 토큰을 한 화면에 설계

근거: `src/styles/splendor-premium.css:12`의 grid는 `market bank` 다음 `treasury reserved`를 새 행에 둔다. `.sp-card`는 그림160px 뒤마다 행동 패널을 붙인다. `TableGames.tsx:214`~222에서 12개 카드 각각에 구매·예약·반환 선택을 렌더한다. 3단 시장 전체를 스캔하기 전에 스크롤이 필요하다.

목표 구조: 상단 얇은 두 선수 점수/차례 레일 → 귀족3명 가로 레일 → 중앙3행×4장 시장, 오른쪽 보석6종 은행 + 선택 행동 패널 → 아래 내 토큰6종/영구 보너스/예약3슬롯. 모든 카드 밑의 버튼을 없애고 선택된 카드 하나만 오른쪽 패널에서 조작한다. 원본 그림은 contain·원래 비율을 유지하고 잘라내거나 숫자를 가리지 않는다. 큰 도움말·로그는 접는다. 공통 헤더와 합쳐900px 안에 넣는 설계를 먼저 검증한다.

합격: KO/ES 모두1440×900에서 12장 시장, 귀족3명, 은행, 내 토큰, 예약, 구매/반환/귀족 선택을 페이지 스크롤 없이 사용. 초기·예약3장·10개 반환·복수 귀족·최종 턴 상태 모두 같은 기준. 44px 행동 목표와 원본 숫자 판독을 동시에 충족. 숫자를 읽을 수 없게 축소해서 통과시키지 않는다.

## 2. P0 — 구매·예약을 선택→예고→확정 흐름으로

근거: `TableGames.tsx:284` 구매,286 예약,217 덱 예약은 바로 `runAction`을 호출한다. 부족 표시는 총 부족개수이고 색별 부족/어떤 토큰을 지불하는지 바로 읽기 어렵다. `splendor.ts` 구매 apply는 보너스→유색 토큰→부족분 금의 고정 지불 순서다.

목표 조작: 카드 클릭/Enter → 원본 확대와 점수·보너스·원래 비용·할인·유색 지불·금 지불·색별 부족을 오른쪽 패널에 표시 → 구매 또는 예약 명시 선택 → 한 번 확정. 예약은 금 지급 유무·예약슬롯 사용·필요 반환을 미리 보여준다. 덱 예약은 뒷면으로 먼저 보여주고 실제 내용을 확정 전 노출하지 않는다. Esc/빈 테이블 클릭은 미확정 선택만 취소한다. 항상 최신 legal action에 선택을 매핑하며 시장이 바뀌면 index만 재사용해 다른 카드를 사지 않는다.

원칙: UI 개선은 기존 합법행동과 엔진을 그대로 사용한다. 선택적 금 지불의 룰 지원이 필요하다면 원 규칙 계약을 확인하고 별도 엔진/서버/action payload/테스트 변경으로 다룬다. UI가 임의 지불 계획을 만들어 서버 검증을 우회하지 않는다.

합격: 금이 있을 때 정확한 비용/부족, 예약3장 제한, 금 은행 고갈, 덱 고갈, 갱신 도중 선택카드 이동, 빠른 더블클릭에서 다른 카드 구매·중복 차감이 없다. 구매/예약은 두 명확한 동작으로 끝난다.

## 3. P0 — 보석 획득·반환 드롭다운을 직접 조작 트레이로

근거: `TableGames.tsx:229`~240는 같은 색2개 즉시 실행 버튼, 서로 다른색 확인 버튼, 여러 반환 계획 select를 다른 곳에 둔다. 엔진 `returnPlans`는 모든 합법 조합을 생성한다. 정상 룰 구현이지만 반환 조합을 긴 문장 목록에서 읽어야 한다. 선택 표시는 부모 `.sp-gem-option.is-picked`에 있고 강조 CSS 일부는 `.sp-gem-pile.is-picked`여서 활성 강조 규칙도 정리할 필요가 있다.

목표 조작: 은행 토큰 클릭하면 선택 트레이에 즉시 임시 토큰을 쌓는다. 같은색2개/다른색3개를 명확한 모드/선택 상태로 표시. 10개 초과 시 내 토큰에서 직접 반환할 색과 수를 +/-로 선택하고 `현재10 + 획득3 - 반환3 = 10`을 고정 영역에서 표시한다. 새로 가져온 토큰을 다시 반환하는 합법 경우와 금 반환도 기존 합법행동 중 정확 일치하는 계획으로만 확정. 선택/취소에는 즉시 시각 반응, 은행에서 실제 차감/성공 소리는 서버 확정 뒤.

합격: 보유8/9/10개, 서로다른 은행색1/2/3/5종, 같은색 은행3/4개, 금 예약으로11개, 토큰0/1개만 가능한 반환, 취소/재선택에서 계산과 실제 payload가 일치. 키보드만으로 완전 수행.

## 4. P1 — 상대 전략과 귀족 진척을 읽게 만들기

근거: `splendor.ts:57`은 `board.ownedBonuses`로 양쪽 공개 보너스를 이미 보내지만 `TableGames.tsx:246`은 ownHand 보너스만 표시한다. 귀족은 요구수치만 나타내고 내 진척을 비교해 주지 않는다. 상대 tokens는 엔진 view에서 총개수만 보내며 `splendor.test.ts:5` 테스트 이름이 tokens private를 명시한다.

목표: 상대 점수 옆에 이미 공개된5색 영구 보너스·귀족점수·예약개수·총 토큰수 레일을 표시한다. 귀족3명에는 내 보너스 기준 `초록2/3` 같은 진행과 충족상태, 선택단계에는 합법 귀족만 선택가능 표시. 구매시 귀족 획득이 예상되면 선택패널에 +3점 예고. 개인정보·예약 카드 얼굴·덱순서·seed·전체 상태는 노출하지 않는다.

기본판의 상대 색별 토큰 공개와 현 앱의 숨김 정책은 상용판 규칙 계약의 차이로 따로 확인해야 한다. 무단으로 private 데이터를 공개하지 않는다. 이번에 공식 규칙 페이지에 접근하지 못했으므로 규칙 동등성 최종 검증을 남긴다.

합격: p1/p2에서 같은 공개 보너스/귀족 진척·정확한 최종 동수턴·동점 최소카드 판정 설명이 보인다. 상대 예약 얼굴/seed는 DOM·네트워크 응답·접근성 트리 어디에도 추가 노출되지 않는다.

## 6. P1 — 모션·효과음이 원인과 결과를 연결하도록 다듬기

근거: `deriveSplendorVisualEvent`(`TableGames.tsx:62`)는 ownHand 증가 중심으로 이벤트를 추론하고 하나의 kind를 고른다. 내 보석 획득은 실제 은행→내 토큰 좌표 flight지만 반환/구매 지불 방향·상대 구매는 같은 수준으로 표현하지 않는다. 카드 구매는 포트폴리오 영역에 나타나는 CSS fold 표현이며 실제 source→destination 전체 이동은 아니다. 이미 shared audio controller와 게임별 큐·8voice cap·기본 음소거·오프스크린 정지가 있다.

목표: 확정 행동을 작은 연속 묶음으로 보여준다. 보석 take→반환, 지불 토큰→은행→구매 카드→영구보너스 +1→귀족 방문 +3→다음 차례. 피드백 slot은 높이를 유지해 레이아웃 점프 방지. 상대는 공개 구매/은행변화만 보여주고 예약 비공개 얼굴은 연출하지 않는다. 로컬 미확정 선택은100ms 안의 outline/lift, 확정 이동은약180~320ms, 귀족 보상은약450~650ms를 초기 튜닝값으로 삼아 직접 플레이로 조정한다. 긴 연출로 다음 턴 입력을 막지 않는다. existing 공유 오디오 호출 한 곳에서 짧은 칩 마찰/카드 플릭/귀족 accent 음색을 다듬으며 새 오디오 라이브러리는 추가하지 않는다.

합격: 구매+귀족+15점이 한 턴에 발생해도 모두 설명되며 성공 음/이동은 한 번만 재생. 숨김탭 복귀·재연결·같은version재전달에서 오래된 모션/소리0회. reduced-motion은 정보만 즉시 보여준다. 실제 노트북/이어폰/스피커에서 연타시 거슬리는 중첩·클리핑·음향 지연을 청취한다. 합성 unit test는 청취의 대체가 아니다.

## 7. P0 출시 관문 — 실제 온라인 한 경기와 오류복구

근거: `docs/SESSION-HANDOFF.md`는 HTTP PGlite fixture와 수동 새로고침 검사이며 실 Supabase Realtime 두기기/전체 경기 미검증이라고 명시. `src/core/client.ts:45`는 SUBSCRIBED만 처리. 공통 재시도 버튼이 새 네트워크 요청을 만들지 않는 문제는 root가 확인했다. `src/core/display.ts`는 fine-pointer1024px이상만 스플렌더 플레이 허용한다. CSS breakpoint가 있어도 터치 모바일 제품이라고 주장할 수 없다.

목표: root 공통 연결상태·확정 요청 중 표시·실제 재조회·재접속 처리를 재사용한다. 게임별 중복 네트워크 시스템은 만들지 않는다. 스플렌더는 선택상태를 최신 view에 검증하고 실패시 미확정 선택을 보존/무효화하는 조건을 명확히 한다. 전용 랭크/매치메이킹/유료계정은 현재 두사람/무료운영 요구에 추가하지 않는다.

합격: 실 Supabase 두기기 KO/ES로 시작→보석반환→공개/덱예약→구매→복수귀족→15점 최종턴→종료 전체 경기. 150~500ms 지연·오프라인10초·새로고침·숨김탭·동시/중복요청에서 양측 버전·점수·은행/내 토큰일치. 성공여부를 몰라도 재전송으로 중복결제하지 않는다. 지원플랫폼은 현재 데스크톱을 명시; 터치지원은 별도 제품 범위가 확정될 때 route 제한과 실제 touch 검증을 함께 바꾼다.

### 기존안3·6의 변경: 단일 kind 중심 연출 → 확정 행동의 순서 있는 결과 묶음

`deriveSplendorVisualEvent`는 `result > noble > purchase > reserve > tokens > market > turn` 우선순위에서 primary kind 하나를 고르지만 purchasedCard/nobleAwarded 등 부가값은 이미 함께 유지한다. 따라서 모든 동시효과가 현재 완전히 사라진다고 표현하지 않는다. 다만 primary kind 위주의 문구/사운드에서는 복합 행동 원인과 지급·반환의 순서가 충분히 보장되지 않는다.

보완 계약은 **validate → 원자적 지불·카드이동 → 시장보충 → 영구보너스/점수 → 귀족자동방문 또는선택 → 최종턴/종료 판정**이다. 실제 판정은 기존 엔진이 맡고 UI 연출은 확정된 결과를 이 순서의 작은 묶음으로 재현한다. 범용 TCG 스택이나 새 전역 이벤트 시스템을 만들지 않고 현재 확정이벤트·공유 피드백 구조를 확장한다. 한 행동에서 purchase/noble/result가 함께 일어나도 한 kind 때문에 사운드/설명이 덮이지 않게 한다.

- own action의 확정 payload와 전후 view를 함께 쓰면 획득 뒤 같은 색반환처럼 net delta가0인 흐름도 표현할 수 있다. net delta만 보고 취득·반환이 없었다고 오판하지 않는다. 실제 요청 승인 전에 지불/입수 성공을 연출하지 않는다.
- 묶음은 방·뷰어·확정버전/sequence로 중복 제거한다. 첫 렌더·늦은 snapshot·오프라인복귀는 현재 상태에 바로 정착하고 과거 묶음을 재생하지 않는다. opponent에는 이미 허용된 공개정보만 사용한다.
- 기존 zones는 tier deck→market→own reserved→구매된 보너스 집계다. 구매 카드를 엔진이 개별 portfolio로 보관하지 않으므로 새 영구 카드이력 zone을 시각효과 목적으로 추가하지 않는다. source 원본 ID와 목적지 보너스의 관계만 연출한다. canonical 90+10매핑·deck/market/reserved 내 중복/보존·취소시 자원 불변은 작은 의미있는 검사로 확인한다.
- 피드백 강도는 선택(작은 lift/outline)·구매(카드이동+보너스)·귀족/승리(초상+점수+accent)의3단계다. 2~3채널부터 시작하고 필요한 만큼만 쓴다. 일반 토큰마다 shake/flash/hit-stop을 넣지 않는다. CSS transform/opacity로 이동하며 overlay는 pointer-events:none. 모션 큐 종료를 다음 턴 input 허용의 조건으로 삼지 않는다.
- 서버 확정 상태를 즉시 기준으로 다음 합법 선택은 계속 가능하게 한다. 턴 넘김 후 눌렀던 confirm을 입력 buffer로 보관했다가 다음 턴 자동 구매하지 않는다. 플랫폼 액션게임의 coyote-time/input-buffer 예제는 적용 대상이 아니다.

필수 검증을 추가한다: **구매+보너스+귀족+15점**, take+동일색반환(net0), 같은version재전달, 늦은 전버전, 카드선택중시장갱신, Enter길게누름, pointer와키보드전환, 모션중다음선택, 방/뷰어전환. 모든 부가효과가 설명되면서 요청·자원차감·효과음은 한 번만 발생해야 한다.

### 기존안6·7의 변경: 음량/성능을 추정 → 프로파일·청취 증거를 남기기

- sound성공은 확정이벤트 한 곳에서만 발생하고 선택 preview와 성공 cue를 구분한다. Web Audio clock을 사용하되 조작을 음악박자에 맞춰 늦추지 않는다. unlock·음소거·숨김탭·방전환·context suspended 기존 방어는 유지한다.
- production `npm run build`/preview에서 대표 최악상태(12장,예약3장,10개반환계획,복합구매/귀족이벤트)를 Chrome Performance/React profiling으로 측정한다. command채택 전 클릭→로컬preview, 확정응답→DOM update, layout/paint, 이미지decode/transfer, heap과50ms이상 long task를 분리 기록한다. 느린 네트워크와 메인스레드 jank를 혼동하지 않는다.
- 동작중60fps(16.67ms/frame)는 목표값이며 아직 측정/달성했다고 쓰지 않는다. 반복행동 후 transient overlay/AudioNode/타이머가 누적하지 않는지 검사한다. 실제 가장큰 비용 하나를 찾은 다음 이미지파생압축·선택후보계산·CSS paint 등을 수정하고 같은 기기/상태에서 전후치를 비교한다. WebP, blanket memoization, 객체pool, 모든아트atlas화를 먼저 적용하지 않는다.

실제 10토큰 경계 + 예약 3칸 상태(`ko-cap10-reserved3.png`, `es-cap10-reserved3.png`)에서 세 색을 선택한 뒤 6개 반환 스테퍼가 보이는 것을 확인했다. 미리 선택된 반환은 빨강1+검정2=3개이고, 표시는 `10 + 3 − 3 = 10/10`; 3개 은행 선택과 6개 반환 스테퍼가 캡처 검사에서 확인됐다. 보드 하단은 KO/ES 모두 890.7px/900px, 가로 넘침 없음, 카드 12장·귀족 3명·은행·보관함·예약 슬롯이 모두 보였다. 반환 불필요한 `0 + 1 − 0 = 1/10` 상태에는 스테퍼가 0개다. 이는 화면상 토큰 합계와 10개 상한을 함께 검증하며, 단위 테스트는 초과분이 정확히 합법행동의 반환 계획과 일치함을 확인한다.

두 기기 온라인 경기와 실제 오디오 청취는 검증하지 않았다.

### 최종 연출·음향 검수

최종 비용 표와 장식 슬롯 정리 뒤 KO/ES의 초기·카드 선택·보석 선택·10토큰 경계 상태를 다시 검사했다. 네 상태 모두 보드 하단은 890.7px/900px이며, 비용이 네 색에 걸친 선택판도 화면 안에 들어왔다. 반환 조작은 최소 44px이고, 원본 카드·귀족 이미지 100개의 해시가 기준 커밋과 일치했다.

`scripts/verify-splendor-quality.mjs`에서 실제 UI의 효과음 설정 버튼으로 Web Audio를 활성화한 뒤 복합 구매를 확인했다. 지불 토큰→은행, 구매 카드→흰색 영구 보너스, 귀족→수령자의 점수 숫자가 순서대로 이동했고, 각 출발·도착 좌표는 캐시된 실제 요소 위치와 1px 이내로 일치했다. 종료 후 이동 overlay는 0개였다. 카드 착지에는 구매 cue의 3개 음, 귀족 착지에는 귀족 cue의 3개 음만 발생했으며, 착지 전 음과 중복 cue는 없었다. 이는 브라우저의 AudioNode 호출·시점 검사이고 실제 스피커 청취 결과는 아니다. 최종 근거는 `output/playwright/splendor-sol/native.json`, KO/ES 캡처 및 `original-art-hashes.json`이다.

### 초보자 그림 가이드 독립 검수 (2026-10-11)

Sol이 KO/ES 설명을 엔진 규칙 및 원본 그림과 대조했다. 서로 다른 색은 가능한 색이 충분하면 정확히 3종, 같은 색 2개는 가져오기 전 은행에 4개 이상, 금은 지불의 임의 색 대용, 예약 최대 3장과 은행에 금이 있을 때만 금 1개, 금 포함 토큰 총 10개 및 초과분 반환을 확인했다. 영구 보너스는 모든 카드의 해당 색 비용을 줄이며 귀족 조건은 토큰이 아닌 카드 보너스로 충족한다. 귀족 3점·여러 명 충족 시 한 명 선택·15점 도달 후 동일 차례 수 종료도 일치한다. 동점의 구매 카드 수 비교는 펼치는 세부 규칙에 남아 있다. 예시 `t1-01`은 초록 비용 4·흰색 영구 보너스 1·1점, `n0`는 흰색/파랑 보너스 각각 4·3점으로 원본 그림 및 canonical 데이터와 일치했다.

소스 동결 뒤 Chromium 헤드리스에서 두 언어 각각 6개 상태를 검수했다: 실제 게임 목록 설명 모달 1440×900, 해당 모달을 390×844로 줄인 상태와 세부 규칙 펼침, 실제 게임 아래 가이드 1440×900, 내보낸 `GameGuide`를 렌더한 읽기 전용 390px 컴포넌트 검사와 세부 규칙 펼침. 실제 모바일 방은 기존 데스크톱 제한 안내를 유지하므로 390px 컴포넌트 검사는 모바일 플레이 지원을 뜻하지 않는다. 모든 12개 상태에서 페이지·가이드 가로 넘침이 없고, 본문 글꼴이 최소 14px이며, 이미지 로드·`object-fit: contain` 및 그림 프레임 안의 이미지/캡션 배치를 확인했다. 모달은 데스크톱에서 900px 너비, 모바일에서 350px 너비로 표시되며 모바일 내용은 내부 세로 스크롤로 끝까지 읽을 수 있다.

Tab/Shift+Tab 초점 순환, Enter로 세부 규칙 펼치기, Escape 닫기, 원래 설명 버튼으로 초점 복귀를 실제 UI에서 확인했다. 모바일 하단 확인 버튼도 스크롤로 접근했다. 근거는 `output/playwright/splendor-guide/native.json`과 `{ko,es}-{modal1440,modal390,modal390-bottom,modal390-detail,below1440,below390,below390-detail}.png`이다. 이 검수에서 런타임 게임 파일을 수정하지 않았다. 물리 모바일 기기 터치·화면 판독과 실제 스피커 청취는 이 환경에서 검증할 수 없다.

닫기 버튼의 추가 검수에서 모바일 내부 스크롤 중 고정 버튼이 본문 위에 겹치는 문제를 발견해 공통 CSS 담당자에게 전달했다. 그림 가이드 모달의 닫기 버튼을 헤더와 함께 스크롤하는 44px 버튼으로 수정한 뒤 KO/ES 1440px 상단 및 390px 상단·하단을 재검수했다. 텍스트 범위와 닫기 버튼의 겹침은 0개이며, 하단에서 Tab으로 상단 닫기 버튼에 복귀하고 Shift+Tab으로 하단 확인 버튼에 복귀했다. Escape 닫기와 원래 설명 버튼의 초점 복귀도 통과했다. 최종 별도 근거는 `output/playwright/splendor-guide/close-native.json`과 갱신한 모달 상단·하단 캡처다.

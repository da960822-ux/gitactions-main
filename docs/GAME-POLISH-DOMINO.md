# Domino table polish and rule contract

Domino is a two-team double-six block game. The engine builds 28 distinct tiles. Singles receive seven each and leave 14 unused; four-seat modes deal seven to every seat and have no draw pile. The engine remains authoritative for the deal, legal placements, turn order, scoring, and round result; the table displays the viewer's hand and public chain while offering only actions the engine allows.

The current new-game contract is rules v2 (Lisbeth); see the bilingual [Lisbeth manual](DOMINO-LISBETH.md). Older verification details later in this file were recorded against earlier rules and remain historical evidence only. Saved v0/v1 games retain their contracts.

## Rule contract

| Area | Contract |
| --- | --- |
| Modes and deal | 1v1: `p1` vs `p2`, 7 tiles each; the other 14 are out of play and are not drawn. The first deal guarantees `6|6`, which opens the first hand. Partners: `p1 + b1` vs `p2 + b2`, seats alternate. Human-versus-bots: `p1 + p2` vs `b1 + b2`. Every four-seat position receives 7 tiles. |
| Later opening | The actual winner of the preceding hand opens the next with any tile from their hand. A double opening earns +30 on any hand. A non-double opening on a later hand earns +60 if the first response passes. In four-seat play, the third seat must then play or the bonus is canceled; no third-seat condition applies in 1v1. |
| Normal hand-out | The first player to empty their hand wins for their team. The winning team scores all pips remaining across all active hands, including its partner. |
| Capicúa | Fixed +30. The final tile that empties the hand must be a non-double that fits both distinct open ends. The winning team adds all pips remaining across all active hands. |
| Tranque | In every mode, block immediately once all seven distinct tiles matching each open-end number have been played. Otherwise, no legal play closes 1v1 after two consecutive passes and four-seat play after four. Compare only the trancador (last placer) with the next seat; lower pips wins and a tie goes to the trancador. Score all pips remaining across all active hands for the winning team. |
| Match length and bonuses | The target is 200 by default, selectable as 100 or 200. Hand scores and bonuses settle at hand end. Paso corrido is disabled. |
| Privacy | A hand remains private to its owner. |

Saved v0/v1 states retain their original target, Capicúa, Paso corrido, and tranque settings. Those legacy contracts are not options in new v2 games.

Settings must be explicit in the pre-game flow and readable during play. Defaults preserve the basic one-hand game. A bonus or alternate scoring rule must not be implied when it is disabled.

## Visual and interaction direction

The current board uses a green radial felt surface with a CSS wood-gradient rim and separate seat cards. A reusable inline SVG component generates all 28 faces (`0 ≤ a ≤ b ≤ 6`) from the 0–6 pip layouts plus one engraved back. It renders at a 120×64 horizontal viewbox or 64×120 vertical viewbox, with layered resin/edge/pip/brass gradients and a shadow; each SVG instance uses unique gradient IDs. These are authored locally, with no external image dependency. Keep pips crisp and correctly arranged at board and hand sizes. The player's hand stays grouped by tile, remains keyboard reachable, and marks playable tiles before selection. Selecting a playable tile exposes its legal left/right end choices; placing it brings the newest tile into view. Long chains scroll horizontally without shrinking tiles into illegibility. Opponent hands display tile backs and public counts, not values.

Use stable space for the turn guide and result/last-action feedback. A placed tile should visibly join the selected end; passes, blocked hands, Capicúa, Paso, and match results should name the event and affected team. Motion is brief and respects reduced-motion settings. The board plays a Domino-specific pick cue on local selection. Confirmed public events map to Domino-specific synthesized place, pass, turn, tranque, Capicúa, Paso, score, round-start, and win cues through the existing audio transport; cues follow deduplicated event sequences, and the terminal result takes priority. This adds no BGM or new audio API. Avoid adding a rendered 3D asset as a placeholder requirement; authored 2D tiles satisfy the visual contract. Consider rendered 3D art only if it can ship as a complete, usable, original asset with a defined role and matching board states.

## Privacy and event contract

During a hand, aggregate scores are `null` in each viewer payload. The view contains only that viewer's `hand`; seat counts and the public chain are visible, while `revealedHands` and aggregate scores appear only after a hand ends. The bounded (40-event) log contains public plays and event metadata, not hands, seed, or stock. Online room snapshots select the `room_views` row for the authenticated user; the full state stays in the service-controlled room-state table, and only the service role can commit state/view pairs. The bot chooser receives its own hand, the public chain/open ends, difficulty, and public pass/count context; it does not receive an opponent's hand. Never include a complete private hand in a public event, action log, diagnostic log, bot trace, or serialized room state available to the other seat. This restriction applies to bot hands as well as human hands. Event feedback must be derived from confirmed authoritative state, not optimistic clicks.

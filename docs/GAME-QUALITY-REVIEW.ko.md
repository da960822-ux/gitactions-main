# 세 게임: 병렬 스킬 검토 및 실행 제안

검토 대상은 다빈치 코드·캐치마인드·부루마블(Marble)이다. 최신 사용자 지시로 뮤직톡톡은 제외했다. 도미노·자이푸르·스플렌더·민화투와 독립 랜딩의 변경도 이번 제안 범위에 넣지 않는다. 공유 파일을 수정할 때에도 대상 세 게임에만 영향을 주도록 한다.

## 적용한 스킬과 근거

## 판단

세 게임은 규칙을 실행하는 웹 UI 단계에서, 반복해서 플레이하고 싶은 게임 제품 단계로 넘어가야 한다. 현재 가장 큰 병목은 자산의 해상도 하나가 아니다. 캐치마인드는 입력·채우기·전송의 정확성, 다빈치는 추리 정보의 배치, Marble은 화면 템포와 경제 선택의 납득성이 먼저다. 자산 교체는 이 문제 해결과 함께 진행해야 효과가 난다.

이미 구현된 것을 인정한다: 조커·타일 직접 선택·추측 확인·재대결, 다양한 그림 도구·힌트·개인 제시어 설정, 40칸·13개 카드·건설·대출·말 선택·공개 이력, 게임별 효과음·모션 감소·서버 비공개 뷰·RLS·요청 중복 방지가 있다. ‘없다’는 전제로 재구현하지 않는다.

## 새로 확인한 문제와 증거의 강도

| 문제 | 확인 수준 | 수정 방법 | 완료 조건 |
|---|---|---|---|
| 캐치마인드 영역 채우기의 소수 픽셀 좌표 처리 | 현재 함수를 임시 번들로 실행. 동일 테두리 안 `(10,10)`은 채워지고 `(10,10.2)`는 실패. 저장 y=.017에 600을 곱하면 10.2가 되어 실제 좌표 경로에 해당 | bucketFill의 경계에서 x/y를 같은 규칙으로 정수화·clamp한 후 인덱스 생성. 정규화 좌표에서 replay까지 같은 계산 | 소수 좌표·가장자리·서버 저장 후 replay 테스트에서 같은 영역/색 |
| 캐치마인드 한글 조합 Enter가 전송됨 | 실제 데모 UI에서 `isComposing=true` Enter 합성 이벤트를 보냈을 때 채팅이 추가되고 입력창이 비워짐. 물리 OS IME는 미검증 | CatchmindChatComposer에서 조합 중 Enter를 무시하고 전송 중 중복 제출 차단. 브라우저별 조합 종료 동작 검증 | Windows/macOS 대상 IME에서 조합 확정은 전송하지 않고 다음 Enter는 한 번 전송 |
| 그리기 제한이 펜 동작이 아닌 전송 조각 수에 걸림 | 실제 엔진에 단일 조각 요청 200개 성공, 201번째 `Round stroke limit reached` 확인 | 임시로 제한을 무작정 높이지 말고 strokeId·segmentIndex를 가진 논리적 펜 동작과 전송 조각을 구분. 점/바이트/속도 제한은 유지 | 80초·설정 최대180초 시나리오에서 정상 드로잉이 조각 수로 끊기지 않고 악의적 요청은 제한 |
| 전송 중 새 pointerDown이 공용 pointsRef를 덮어씀 | 코드상 위험. 지연/실패 주입으로 전체 재현은 미완료 | 현재 펜 입력 버퍼와 전송 대기 큐를 분리. 큐마다 strokeId·색·굵기를 고정하고 승인된 조각만 삭제 | 800ms 지연·실패·연속 두 선·색 변경에서 유실/연결선/잘못된 색 0건 |
| Marble 화면·소리 큐 간격 불일치 | 코드상 이벤트 화면 간격640ms, 음향 간격230ms. 4개 큐의 마지막 시작은 각각1,920ms/690ms; 실제 청취 미검증 | 대상 게임의 공개 sequence를 기준으로 하나의 표시 타임라인이 화면·음을 함께 시작. 서버 상태나 다음 행동을 오래된 연출에 묶지 않음 | 한 사건의 카드·강조·음향이 함께 시작하고 재접속/좌석 변경 때 과거 이벤트 재생 없음 |
| 캐치마인드 선택 대기 상태 문구 불일치 | 실제 p2 화면에서 준비 중/상대 선택 중/상대 그리는 중 혼재. 코드 역할/단계 분기 확인 | 공개 phase와 viewer role을 분리한 동일 파생값에서 헤더·사이드 라벨 계산 | 양측·모든 phase의 문구가 같은 사건 설명 |

320ms 주기마다 조각 하나가 저장된다면 200개는 약64초다. 기본80초보다 짧지만 이는 연속 주기 전송을 가정한 계산이며 실제 플레이 시간 측정 결과는 아니다. 빠른60점 청크 분할·네트워크 지연·펜 정지가 결과를 바꾼다.

## 게임별 수정 및 자산 업그레이드 방향

### 다빈치 코드

냉정한 평가: 추리의 소재는 충분하다. 그러나 적은 타일도 거대한 패널 안에 흩어져, 공개 정보의 관계를 읽는 시간이 UI를 훑는 시간으로 바뀐다. 더 많은 배경 그림보다 타일의 대비·정렬·선택 상태가 중요하다.

- 수정: 상대 랙/내 랙/현재 뽑은 타일/추측 숫자를 같은 시야에 놓는다. 서버가 허용한 현재 행동만 강조한다. 짧은 ‘선택 → 추측 → 공개 페널티’ 튜토리얼을 제공하되 방 진입 시 강제 규칙 모달은 만들지 않는다.
- 자산: 검정·상아 타일의 재질·실루엣을 정돈하고 선택/공개/신규 뽑기 상태를 구별한다. 숫자·조커·색 라벨은 코드 텍스트로 유지하여 선명도·번역·비공개 데이터 보호를 지킨다. 배경은 저대비 재질 하나로 끝낸다.
- 새 기능 후보: 본인이 직접 후보 숫자를 표시하는 개인 메모. 서버 비밀값으로 정답 확률을 계산하지 않는다. 랙에 새 타일이 삽입될 때 숫자 index로 메모를 잘못 붙이지 않도록 안정적인 비공개-safe 식별/위치 추적을 먼저 설계한다.
- 수정 위치: DaVinciTable.tsx와 해당 스타일, 공개 이벤트 파생/MatchSummary. 후보 메모는 별도 비게임 상태이며 게임 엔진 규칙을 바꾸지 않는다.
- 합격: 1366×768/1440×900 양 언어에서 두 랙과 현재 행동을 페이지 스크롤 없이 비교. 비공개 상대 숫자는 DOM·asset명·data 속성·접근성 라벨 어디에도 없어야 한다.

### 캐치마인드

냉정한 평가: 그림 도구는 충분하다. 아직은 ‘그리기와 맞히기가 기분 좋게 이어진다’보다 도구·상태·채팅이 따로 동작하는 느낌이다. 기능 오류와 입력 반응을 놔두고 캔버스에 예쁜 종이 질감을 추가해도 품질이 오르지 않는다.

- 수정: 위의 채우기·IME·버퍼 문제부터 처리. 제시어/타이머/역할/점수는 한 HUD, 정답 입력은 캔버스 바로 옆 또는 아래의 항상 보이는 위치로 정돈한다. 중복 점수와 오답 목록은 합친다.
- 자산: 실제24~32px에서도 읽히는 일관된 SVG 도구 아이콘, 선명한 활성/비활성/포커스 상태. 그림 캔버스는 깨끗한 단색을 유지한다. 정답·시간 종료·패스의 결과 마크는 모양과 텍스트로 구분한다.
- 새 기능 후보: 검수한 언어별 허용 정답 목록, 라운드 결과 카드(본인들이 그린 그림+양 언어 정답+성공시간). ñ와n을 무조건 같게 만들거나 AI 번역 결과를 즉석 정답으로 인정하지 않는다. 결과 이미지 저장은 두 사람 동의·삭제 범위가 먼저다.
- 구현: 제시어와 허용 정답은 동일한 개념ID로 서버 판정. 과거 저장방과 Edge 번들도 함께 버전 관리한다. 선 전송은 logical stroke/segment로 분리하고 승인·retry·순서를 명시한다. 렌더링 최적화는 프로파일 뒤 결정한다.
- 합격: 새로고침한 상대 캔버스와 드로어 캔버스가 동일하고 fill/undo가 한 펜 동작 단위로 일관됨. 정답은 guesser에 먼저 노출되지 않는다. 물리 IME·느린 네트워크·긴 그림을 확인한다.

### 부루마블 / Marble

냉정한 평가: 40칸·건설·대출이 있다는 사실과 의미 있는 전략이 생겼다는 사실은 다르다. 현재 작은 보드 글씨, 큰 중앙 공백, 길어질 수 있는 이벤트 큐가 의사결정을 약하게 만든다. 고해상도24개 도시를 한꺼번에 그리기보다 소유/건설/도착 도시가 또렷하게 읽히게 해야 한다.

- 수정: 칸에는 도시명·소유·건설단계만 우선 노출. 중앙/옆 패널에 선택한 도시의 매입비·통행료·건설 전후·남는 현금을 크게 보여준다. 기존40칸을 줄이거나 저장방을 초기화하지 않는다.
- 자산: 2인 소유 표식과3단계 건물 실루엣,6개 말, 황금열쇠/이벤트 계열을 같은 카메라·광원·윤곽으로 제작한다. 도시 미술은 보드 초소형 썸네일보다 도착 상세 카드의 대표2개로 먼저 검증한다. 국기·지명·금액은 코드로 유지한다.
- 경제: 같은3단계 투자300에 광주 임대료는12→96(+84), 밴쿠버112→896(+784)이다. 추가 임대수익 차이는 약9.33배. 이것은 실제 승률이나 도착 확률을 반영한 수익률이 아니다. 다만 투자 선택이 도시별로 얼마나 다른지 수치로 확인해야 한다는 근거다.
- 새 기능 후보: 도시 저당 또는 건물 매각 중 한 가지. 단순 벌금/보너스 카드를 늘리는 것보다 손실을 감수한 현금화 선택이 전략을 만든다. 적용 전에 비용곡선·세트 보상·부담금과 함께 실험한다.
- 합격: 1366×768/1440×900에서 주사위·현재 돈·도착 도시·주 행동이 한 시야에 들어감. 소유/건설이 무채색에서도 구별됨. 거래 효과는 실제 moneyDelta로만 표현. 빚/순자산/파산 원인이 양측에서 일치.

## 제작 방법

아트 제작의 공통 순서: 실제 표시 크기에서 회색 형태 테스트 → 대표 타일/도구/말 한 세트 선정 → 동일한 시점·광원·팔레트로 소량 제작 → 알파·크기·여백 검사 → 네이티브 크기 contact sheet → 실제 게임 캡처 → 그때 전체 자산 확장.

UI 텍스트·가격·숫자·아이콘 상태를 큰 이미지에 구워 넣지 않는다. 단순 기하학 아이콘은 SVG, 재질/도시/말은 필요한 경우 WebP/PNG를 사용한다. 생성형 도구는 컨셉/원화 생산 수단이며 알파·치수·일관성·권리 확인을 대신하지 않는다. 경쟁사 스크린샷에서 이미지를 추출하지 않는다.

최소 시각 제작 명세는 6개 자산군/30개 항목이다. 기존 타일 비트맵이나 말6종 전면교체는 포함하지 않는다.

| 자산군 | 수량 | 제작 크기 | 실제 표시 크기/목적 |
|---|---:|---|---|
| 다빈치 상태 기호 | 6 | 24×24 SVG | 16~24px; 선택/공개/대기 의미 |
| 캐치 도구 기호 | 8 | 24×24 SVG | 20~24px 그림,44px 클릭영역 |
| 캐치 단계 그림 | 3 | 160×120 SVG | 80×60~120×90; 사용자 그림보다 작게 |
| Marble 특수칸 기호 | 8 | 32×32 SVG | 24~28px; 현재 대형 아틀라스 대신 |
| Marble 도시 상세 | 2 | 320×320 WebP | 160×160px; 광주/산토도밍고부터 |
| Marble 건설 단계 | 3 | 32×32 SVG | 14~20px+단계 숫자 |

Marble collector/special WebP 원본 합계는1,977,288+1,796,666=3,773,954바이트다. 작은27px 슬롯에 상세한 미니어처를 쓰는 대신 벡터 기호, 원본도시는 lazy 상세로 역할을 나눈다. 실제 초기 다운로드 비용과 FPS는 별도 측정한다. 목표예산은 다빈치40KB,캐치100KB,Marble초기180KB+도시상세200KB이며 새/개편 시각파일만의 제안 목표다. JS·폰트·오디오를 합친 총페이지 크기라는 뜻이 아니다.

구체 가족별 팔레트·포맷·제작 브리프는 아트 보고서와 asset-upgrade-manifest.json을 따른다. 이 표는 최초 planned 명세다. 실제 제작·통합된 자산은 하단 구현 기록과 GAME-ART 문서, 부루마블 시각 제작 계획을 따른다. 음향 보고서의39클립은 확장할 때의 전체 라이브러리 후보다. 첫 샘플은 타일2·주사위2·동전2·카드1·정답1의8개 정도로 제한하고 기존 합성음과 A/B 청취한다. 이 샘플이 더 선명하지 않으면 파일 교체를 확장하지 않는다. default mute·사용자 제스처 unlock·음량 설정·동시 voice 제한은 보존한다.

## 최초 분석 당시의 검증 범위

아래는 구현 전 분석 기록이다. 현재 구현·검증 결과는 문서 하단과 별도 검증 보고서에서 확인한다. 게임 소스 기준은 `59d10472ddde64809d0a6702a54a447087f17dc8`. 지난 온보딩의 테스트326개/전체빌드 성공은 현재 코드 기반 검증이며 이번 제안의 구현 성공이 아니다. 이번에는 소스·게임 규칙·자산을 변경하지 않았다. 재현/보고서/임시 번들은 체크아웃 밖에 저장했다.

실제 네트워크 p95·최저사양 FPS·전체 세 게임 완주·실제기기 음향·물리IME는 미검증이다. 후보메모/저당/결과카드 등은 제안이며 구현된 기능으로 표현하지 않는다. 비교 사이트는 이전 요청에서 프록시403으로 차단되어 최신 경쟁사 직접 플레이 조사로 주장하지 않는다.

## 이번 구현에서 적용한 변경

기능은 Luna, 자산·이벤트 타임라인은 Sol 에이전트가 병렬로 담당했고, 통합 단계에서 실제 화면의 정보 밀도와 조작을 다시 검토했다.

- 부루마블: 24개 도시 SVG, 6종 말의 실루엣 보강, 특수 칸·건설 3단계 심볼, 선택 도시의 가격·현재 통행료·다음 건설비·예상 통행료 표시. 신규 판은 도시 가격의 40%/60%/80%를 각 단계 건설비로 사용한다(10 단위 반올림, 최소 40). 자산 계산도 실제 건설비를 반영한다. 이전 저장 판의 고정 100 규칙은 유지한다.
- 부루마블 이벤트: 공개 이벤트 한 타임라인에서 카드 표시 직후 음향을 예약한다. 비용 부과·미지급 위기·실제 결제를 구분하고 플레이어/은행/공동 기금 사이의 지급 경로를 표시한다. 초기 화면·좌석 변경에서 과거 음향을 재생하지 않는다.
- 캐치마인드: 정수 픽셀로 채우기 계산, 논리적 stroke ID와 순번 기반 조각 병합, 순서 보장 전송 큐, 실패 시 명시적 재시도. 채우기/실행 취소는 전송 큐를 기다린다. 한글 조합 Enter와 전송 중 중복 제출을 차단한다. 상태 라벨·도구 심볼·단계 일러스트를 보강한다.
- 다빈치: 상대 패와 내 패를 나란한 행동 패널 옆에 배치한다. 선택/공개 상태 심볼과 추측 확인의 포커스 이동·Escape 복귀를 적용한다.

## 상용화 판단과 다음 작업

이번 수정만으로 상용화 품질을 충족했다고 판단하지 않는다. 다음 단계의 합격 기준을 충족해야 한다.

1. **경제 검증**: 신규 건설비는 가격 위계를 복원하는 1차 규칙이다. 다수 seed의 시뮬레이션과 실제 사람 대전으로 선공 승률, 파산 시점, 저가/고가 도시 투자 효율, 대출 사용률, 게임 길이를 측정해야 한다. 표본 없이 '균형 잡힘'이라고 단정하지 않는다.
2. **도시·건물 연출**: 현재 도시별 SVG는 상세 카드에서 사용한다. 보드용 축소 자산과 확대 자산의 일관성을 실제 플레이로 검사하고, 건설 시 단계 변화와 소유자 구분을 더 강화한다. 거래·경매·저당은 아직 구현하지 않았으며 별도 규칙 설계가 필요하다.
3. **실제 온라인 검증**: 두 독립 클라이언트에서 800ms 지연·일시 실패·재접속을 넣어 그림 유실, 중복 결제, 이벤트 재생, 숨은 정보 노출을 확인해야 한다. 로컬 데모와 DB 단위 검증은 운영 Realtime 검증을 대체하지 않는다.
4. **입력·접근성**: Windows/macOS 물리 한글 IME, 키보드만 사용하는 플레이, 효과음 실제 청취, 모션 감소를 검사한다. 합성 키 이벤트 검증과 오디오 예약 시간 측정만으로 기기 경험을 보증하지 않는다.
5. **다빈치 개인 추론 메모**: 타일의 안정적 식별자를 먼저 설계한다. 정렬 후 위치만으로 메모를 연결하면 다른 타일에 후보가 붙을 수 있으므로 이번 구현에서 제외했다.

자산의 파일별 용도와 제작 출처는 [GAME-ART.md](./GAME-ART.md), 기계가 읽는 명세는 [game-art-manifest.json](./game-art-manifest.json)에 기록한다. 생성된 도시 WebP 2종은 참고 시안이며 현재 게임은 일관된 SVG 도시군을 사용한다.


## 상용 게임에서 가져올 설계 기준

[MONOPOLY GO!](https://www.monopolygo.com/)는 게임말·도시·건물이 판 위의 물체처럼 읽히는 시각 체계를 비교 대상으로 삼는다. [Board Game Arena](https://boardgamearena.com/)는 정확한 공개 정보와 합법 행동의 구별, [Gartic Phone](https://garticphone.com/)은 그림이 주인공인 화면과 턴별 상태 전달을 비교 기준으로 삼는다. 경쟁사 그림을 복제하거나 추출하지 않는다. 최신 사이트 직접 플레이와 현재 버전 비교는 환경 프록시의 외부 사이트 403 차단으로 검증하지 못했다. 위 항목은 제품 방향을 설명하는 기준이며 최신 화면을 관찰했다는 주장이 아니다.

추가 부루마블 그래픽 제작·통합 계획은 [MARBLE-VISUAL-PLAN.ko.md](./MARBLE-VISUAL-PLAN.ko.md)를 따른다. 중앙 세계지도, 보드 칸의 24종 도시, 6종 말, 3종 건물, 소유권 카드 프레임은 글자나 이모지로 대체하지 않는 실제 이미지/벡터 자산이다.

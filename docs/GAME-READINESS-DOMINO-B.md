## Detector findings and contextual review

**CLI:** no source-level findings (`[]`). This clean result is not a substitute for runtime evidence; the injected browser detector did find styled text and structural patterns.

**Browser detector:** 22 annotations, not 22 independent product defects. Confirmed contrast concerns are the shared room-close text (`#9d6656` on `#17121b`, 3.9:1; [app.css:98](../src/styles/app.css#L98)) and the board subtitle/footer (`#707c75` on `#fffefa`, 4.3:1; the board-card scope sets `--ink-faint` at [app.css:485](../src/styles/app.css#L485), used by [app.css:156](../src/styles/app.css#L156) and [app.css:227](../src/styles/app.css#L227)). These normal text colors are below WCAG 2.2 AA 1.4.3's 4.5:1 threshold. The two 10px Domino labels in seat/team badges and the 10px board kicker are real small-text findings ([domino-premium.css:169](../src/styles/domino-premium.css#L169), [domino-premium.css:256](../src/styles/domino-premium.css#L256)); they are secondary labels, but the seat/team label helps distinguish roles. The 11px seat-count label and the long Spanish quick-guide tip are also real measurements. The tip is not clipped and appears on two lines at 1440px; its length preserves the requested pass counts, default blocked-hand scoring, settings exception, and tie outcome.

The remaining annotations need context before being treated as defects:

- Six “nested cards” annotations identify the intentional table composition: scoreboard, seat cards, felt/chain, and hand areas sit inside the board/table frame. Their containment conveys the physical game table and its regions.
- “Cream/beige page background” identifies the light Domino board surface (`.board-card`), not the page background. The surrounding app remains plum, while the board and ivory tiles use the colors specified for the Domino surface.
- The `0.06em` letter-spacing finding lands on the room invite identifier, not paragraph copy.
- The two avatar contrast measurements apply to initials that are immediately repeated by adjacent player names; they are secondary identity marks, not the only identity cue.
- Tiny-text findings in the demo banner, reaction helper, and “Otros juegos” footer belong to the shared room shell rather than the three Domino source targets.

## Rule, privacy, and snapshot-animation gates

The current engine is the authority for opening and play rules: `openingRank` assigns doubles a rank above non-doubles; the dealt hand with the highest rank starts, with highest pip sum used if no double exists ([domino.ts:21](../src/games/domino.ts#L21), [domino.ts:110](../src/games/domino.ts#L110)). A pass is valid only with no legal placement; two consecutive passes in 1v1 or four across a four-seat game end a blocked hand. Team remaining-pip totals are the default comparison, and `lowest-player` is an explicit option ([domino.ts:58](../src/games/domino.ts#L58), [domino.ts:67](../src/games/domino.ts#L67)). The guide's 4|4 is labelled an example, not a guaranteed deal.

The board does not add a shared/private-state channel. Current hand labels and `data-domino-a/b` occur on the viewer's own selectable tiles; the chain attributes describe public played tiles. Opponent seats render backs from public counts until the server marks a round result, then the result view may reveal the remaining hands. Board tests verify unrevealed hidden hands do not render and the final four-seat result includes 28 tile elements. The local browser confirmed the pre-result shape after an accepted opening move. This is client-DOM evidence, not a security proof for server responses.

Motion initialization is quiet for an already-present log, and new motion is driven by fresh sequence events. Identity change, sequence regression, document visibility, terminal events, and reduced-motion paths clear/settle queues rather than replaying stale flights ([DominoEventStage.tsx:106](../src/app/DominoEventStage.tsx#L106), [DominoEventStage.tsx:203](../src/app/DominoEventStage.tsx#L203)). Unit coverage tests sequence de-duplication; production two-client snapshot repetition and a live visual animation replay test remain separate gates.

One source-level accessibility gap remains: the event stage is a `role="group"` with an accessible label, but it is not an `aria-live` region ([DominoEventStage.tsx:235](../src/app/DominoEventStage.tsx#L235)). A screen-reader user may hear the general turn-status change without hearing event-specific pass/bonus/result details. Add or verify a polite announcement path before claiming equivalent event announcements.

## Readiness decision

Assessment B supports that the final local Domino UI is coherent and playable for the reviewed desktop demo path, with legal opening selection, stable/private hand rendering, public result gating, and scoped sequence logic. The CLI scan was clean; the browser scan exposed several small-text/contrast issues and several contextual false positives.

This is **not a commercial-readiness sign-off**. Full-round two-device Supabase verification, pass and blocked result in a live game, a four-seat result screen, stale/duplicate snapshot motion, actual browser zoom, physical-device touch/audio, screen-reader event announcements, player comprehension testing, and real-world performance measurements remain outstanding. The `<100ms` response and `<16.7ms` frame figures are targets from the plan, not measurements.

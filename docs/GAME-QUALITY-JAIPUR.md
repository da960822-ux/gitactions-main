# 자이푸르 상용 품질 개선 제안

대상: `origin/main` 59d1047. 앱 코드는 수정하지 않았다. AGENTS.md와 Ponytail full을 적용했다. 최신 소스, 엔진/컴포넌트/모션 테스트, SESSION-HANDOFF, GAME-POLISH-JAIPUR, QUALITY-VISUAL-AUDIT를 읽었다. 아래의 화면 측정은 저장소에 남은 기존 감사 기록이며 이번 세션의 새 플레이 결과가 아니다.

## 시장 비교의 범위

온라인 비교 대상은 Board Game Arena의 Jaipur이다: https://boardgamearena.com/gamepanel?game=jaipur . 출판사 및 공식 규칙 확인 후보: https://www.spacecowboys.fr/jaipur . 두 주소를 정상 HTTPS 경로로 읽으려 했으나 환경 프록시가 CONNECT 403을 반환했다. 따라서 현재 경쟁사 UI, 실플레이, 지원 플랫폼/기능을 확인했다고 주장하지 않는다. 아래는 현재 코드에서 증명되는 부족함과 온라인 보드게임의 실사용 품질 기준을 비교한 제안이다.

현재 게임에는 이미 21개 SVG 상품 구성, stable card ID, 공개 이벤트 기반 카드 이동/동전/보너스 모션, 게임별 효과음, 키보드 포커스, reduced motion, 모바일 탭, 비공개 손패 보호, 서버 legal action gating, 정산 내역이 있다. 필요한 일은 이들을 다시 만드는 것이 아니라 실제 플레이 화면과 조작 흐름에 맞게 완성하는 것이다.

## 1. 규칙의 제품 기준부터 확정 — P0, root와 별도 결정

현재 계약은 낙타 무리를 교환에 사용하지 않기, 매 라운드 p1 시작, 기존 동점 처리, 덱이 0이면 즉시 종료를 명시적으로 보존한다. 엔진 `src/games/jaipur.ts:48`, `:61`, `:63`, `:73`, `:87`도 이를 구현하고 테스트가 고정한다. 공식 자이푸르를 기대하는 사용자를 대상으로 삼는다면 일반적으로 알려진 낙타 반환 교환, 패배자 선공, 보너스/상품 토큰 동점 비교, 시장 보충 불가 시 종료와 대조해야 한다. 현재 교환은 같은 상품을 서로 반환하는 조합도 걸러내지 않는다. 상품 토큰 옷감/향신료의 `[5,4,3,3,2,2,1]`와 3장 보너스 `[1,1,2,2,3,3,3]`도 공식 실물 구성에 재대조할 항목이다. **공식 원문은 차단되어 이 비교를 이번에 확정하지 않았다.**

필요한 결과는 공식 룰과 현재 룰의 차이표, 사용자 의도에 맞는 제품 설명이다. 현재 진행 점수를 양쪽에 공개하고 획득 보너스를 공개하는 정보 공개 방식(`makeView():76`)도 공식 획득 토큰의 앞뒤 처리와 대조한다. 기존 규칙을 유지하면 로컬 규칙임을 정확히 안내한다. 공식 규칙으로 바꾸기로 정하면 UI polish와 분리하고 새 rules version/이전 경기 호환을 설계한다. 임의로 엔진이나 보상값을 변경하지 않는다. 검증은 55장/11낙타, 7장 제한, 귀금속 2장, 6·7장 판매, 동점/마지막 덱/라운드 선공/구 저장 상태를 포함한다. 실제 판매/공개 배포에 필요한 이름·이미지·판권 사용 검토는 root 공통 과제이며 현 자료로 권리 보유를 단정하지 않는다.

## 3. 버튼 목록 대신 손패에서 거래 — P0

현재 `JaipurBoard.tsx:144`는 손패를 교환 모드에서만 클릭하게 한다. 판매는 `:119`–`:127`에서 상품별 모든 수량을 별도 버튼으로 펼친다. 시장 클릭은 단일 가져오기/낙타 전체 가져오기를 즉시 실행한다. 합법성은 있지만 사용자가 카드와 거래 결과 사이를 이동하며 판단해야 한다.

제안 흐름: 시장 클릭은 선택과 짧은 결과 요약을 먼저 보이고 하나의 가져오기 버튼으로 확정한다. 낙타 클릭은 현재 시장 낙타 전부를 함께 강조한다. 손패 상품그룹 클릭은 판매로 들어가 수량 +/−와 3/4/5+ 보너스 가능 표시, 최소 장수/남은 상품토큰/확정 가능한 첫 토큰값을 같은 트레이에 보여준다. 교환에서는 내패와 시장의 선택 개수를 `내 상품 2 ↔ 시장 2`로 보여주고 부족한 쪽을 명시하며 맞는 legal action이 있을 때만 확정한다. Escape/다시 탭으로 취소, 서버 승인 전에는 거래 완료 효과를 내지 않는다. 초기 확인 없는 오탭보다 거래당 한 번의 명확한 확정이 기본값이며 제스처 단축은 이후 실제 사용성 결과로 결정한다.

구조: 기존 choices/runAction/busy/error 재사용, 하나의 로컬 선택 상태와 행동 트레이. 현재 toggle의 최대5 제한은 교환 전용이다. 판매에는6·7장도 가능해야 한다. 현재 판매 action은 상품/수량이며 엔진은 해당 상품의 앞 N장을 판다. 따라서 그룹 수량 방식으로 앞 N stable ID를 표시해 실제 모션과 일치시키고, 임의 카드 ID 판매 API는 추가하지 않는다. 판매 예측은 비공개 아래 토큰값/보너스값을 추측해서 노출하지 않는다.

합격: 금1장 선택 시 왜 팔 수 없는지 이해, 금2장/가죽1장/상품6·7장 판매, 교환2–5장/개수불일치/선택취소/손패7장 가져오기불가를 두 언어에서 직접 검증한다. 100번 중 빠른 이중탭이 서버 행동2개를 만들지 않고, 거절되면 손패가 사라지지 않으며 합법적인 선택을 복구할 수 있어야 한다.

## 4. 상품 그림을 완성된 카드 아트로 — P1

`JaipurArt.tsx:96`–`:108`은21개의 직접 작성된100×100 상품 SVG를 사용한다. 이는 이미 있는 자산이며 삭제할 이유가 없다. 기존 감사는 단독 아이콘과 빈 카드 면적 때문에 큰 대시보드 패널처럼 보인다고 기록한다.

제안: 사막 시장·상점 천막·상품 포장이라는 하나의 시각 방향 아래 세로 카드프레임을 만든다. 7상품 각각의 구별되는 배경/테두리/큰 실루엣, 상하 귀퉁이 상품표식, 읽을 수 있는 이름을 제공한다. 토큰은 카드와 같은 상품표식을 쓰며 적층 높이는 개수, 앞면은 알려진 최고값만 표현한다. 뒷면/덱/낙타 휘장도 같은 화풍과 재질을 쓴다. 우선 대표3상품 시안을 실제 크기로 승인하고 기존21구성에 적용한다. 유명 게임의 그림을 복제하거나 이름만 다른 그림을 무차별 생성하지 않는다.

필요 자산: 기존 SVG를 기반으로 한7상품 얼굴 시스템, 공통뒷면1개, 상품토큰6표식, 보너스앞뒤, 낙타휘장. 카드ID→기존variant 매핑을 유지한다. 합격은100% 실제 화면에서 금/은/가죽/낙타를 색 없이도 즉시 구별, 상품그림/접근성라벨/엔진값 일치, 화면축소/웹폰트실패/KO·ES 줄바꿈에도 값이 잘리지 않는 것이다.

## 5. 이미 있는 효과를 손에 맞게 조율 — P1

`jaipur-motion.ts:44`–`:67`에 가져오기/왕복교환/낙타/판매/동전/보충/보너스 경로가 있으며 `JaipurMotion.tsx:138`은 실제 zone 좌표로 모션을 배치한다. `audio.ts:187`–`:221`에는 전용 카드·선택·교환·낙타·판매·동전·보너스 소리가 있다. 그러나 현재 토큰 도착지는 화면 밖이며 실제 스피커 품질은 미검증이다. 승부를 끝내는 행동은 서버에서 다음라운드를 자동 생성하므로 현재 점수0과 이전 판매동전 연출이 동시에 보일 수 있는 구간도 점검해야 한다.

제안: 선택은 즉시 들림/작은 카드 들림, 승인된 거래는 이동→도착/소리→점수반영의 박자로 일치시킨다. 초기 기준은 선택100ms 이내, 카드 이동180–260ms, 복수카드35–55ms 간격, 판매전체1초 내로 삼고 플레이로 조정한다. 금속토큰/종이카드/낙타의 소리를 구별하고 과한 반짝임과 중복 chord를 줄인다. round-end/round-start는 동일 서버 이벤트를 사용해 이전 정산과 현재 새 라운드를 분명히 구분한다. 서버 자동 진행이나 p1 선공에 새 확인 gate를 넣지 않는다.

구조: 기존 큐/transport/zone 유지, 애니메이션 CSS/오디오 envelope와 실제 길이 조율, 필요하면 기존 transport 안에 직접 녹음하거나 이용권이 확실한 짧은 로컬 샘플 사용. 새 BGM/유료 API는 불필요하다. 합격은 두 좌석에서 실제 판매→보너스→라운드→승리, 빠른 다음행동/리사이즈/언어변경/탭복귀에 카드 순간이동·오래된 큐·중복음 없음; reduced motion/무음에도 판매상품·확정점수·결과를 이해함이다. 물리 iOS/Android/스피커에서 실제 청취와 지연을 확인해야 한다.

## 6. 끊김과 다시 접속도 거래 흐름의 일부 — P0, root 공통

현재 run():59–69에는 busy와 실패 메시지가 있고 엔진/서버의 승인·재시도 방어도 있다. 이는 유지한다. 기존 네이티브 QA는 Realtime 없는 PGlite HTTP fixture에서 상대를 새로고침했으며 실제Supabase 실시간 전송은 검증되지 않았다. root 감사에서 공통 client 구독은 SUBSCRIBED만 다루고 연결상태 노출이 없으며 오류의 다시시도는 현재 snapshot만 읽는 문제가 확인됐다.

제안: 플레이어가 `연결됨/보내는중/재연결중/최신상태불러옴`을 거래트레이 옆에서 알게 한다. 잠깐 끊기면 선택을 가능할 때 보존하고 확정행동은 서버 버전/요청ID에 맞춰 한 번만 적용한다. 응답만 유실된 판매는 재접속 후 이미 판매되었음을 표시하고 카드/효과음을 다시 실행하지 않는다. 룸을 떠났다가 돌아오면 최신 손패/턴/정산으로 시작한다.

필요 구조는 root의 기존client/룸shell에 상태와 실제 refetch/rejoin을 연결하고 Jaipur의 local selection을 authoritative 변경 시 재검증하는 것이다. 거대한 네트워크 프레임워크나 유료매칭은 추가하지 않는다. 합격은 독립적인 두 실제브라우저/기기로 새로고침 없이 완주, 네트워크 끊김5초·30초·백그라운드복귀·응답유실/중복재시도에 행동1회·상대최신상태·개인패비노출이다. 목표전송시간은 실환경 정상 네트워크에서상대보드p95 500ms 이내로 정해 측정하고, 보장된 현재 성능인 것처럼 말하지 않는다.

## 7. 첫 경기와 모바일 완주를 검증 — P1

현재 모바일390×844 테스트는 초대/시작/낙타탭/개인패/44px/폭/reduced motion을 검증했다. 실제모바일 한경기·복잡교환·Safari·실청취 검증은 아니다. `jaipur-premium.css:192`는 내패4열로 다음줄을 만들며 판매목록도 늘어나므로 모바일에서 두 구역을 오가는 문제가 남는다.

제안: 모바일시장5장은 고정 작은 얼굴, 내패는 아래44px이상 클릭영역을 가진 상품그룹 랙, 행동트레이는 손가락이 닿는 하단으로 둔다. 세부 상품보급정보는 작은 펼침판으로 보되 선택중인 거래를 가리지 않는다. 첫 경기에는1장가져오기/낙타/2대2교환/3장판매의 짧은 연습을 기존 엔진의 고정상태로 안내한다. 실제게임에서는 불가능이유(손패가득/최소장수/상품토큰고갈)를 현재 대상에 표시한다. 키보드Tab·Enter·Space·Escape와 스크린리더 상태문은 별도게임모드를 만들지 않고 기존controls에 넣는다.

합격은 규칙을 모르는두 사람이 도움말을 반복해서 열지 않고 기본4행동 수행, 실제모바일390×844와다른높이/landscape에서복잡교환·6장판매·연속라운드 완주, 키보드만으로거래, 텍스트명/아이콘/선택테두리로색각구별, 손패/보너스비공개가접근성라벨에도유지다.

### 수정 방법 A — 행동과 화면 흐름을 명확히 분리

- `JaipurBoard.tsx`의 `choices`, `run`, `busy`, `error`를 재사용한다. UI는 `take/exchange/sell` 의도와 선택 상품·수량만 갖고, 엔진의 legal action을 찾은 뒤 기존 runAction에 보낸다. 새로운 입력 프레임워크나 게임패드 재매핑 화면은 필요 없다.
- discrete action은 HTML button의 한 번의 click activation으로 처리한다. keydown과 click에서 동시에 confirm을 호출하지 않는다. 키를 길게 누를 때 반복 submit, pointerdown 다음 click의 중복 submit, double tap, touch scroll 후 오인 클릭을 검증한다. guard는 요청 시작 즉시 적용하고 기존 요청 ID/서버 검증을 최종 방어로 유지한다. 플랫폼게임의 입력 버퍼/coyote time은 턴제 거래에 적용하지 않는다. 끊겼을 때 눌렀던 판매를 다음 턴에 자동 실행하는 버퍼도 만들지 않는다.
- 실패 시 기존 run이 선택을 보존하는 경로를 유지하고, 메시지를 해당 행동의 실패 이유로 구체화한다. 재조회로 시장/손패/턴이 바뀐 경우 stale index를 그대로 다시 보내지 않고 stable ID로 같은 카드가 남았는지 확인한 뒤 현재 legal action을 재검증한다. 복구할 수 없으면 취소 이유를 표시한다.
- 초안의 `Escape`는 전역 무조건 초기화가 아니라 현재 최상위 대상만 취소한다. 예: 열린 도움말 닫기 → 상품 상세 닫기 → 거래 선택 취소. 닫힌 패널의 이전 카드/버튼으로 포커스를 돌려준다. 간단한 패널 구성에는 일반적인 작은 open panel state면 충분하며 범용 screen stack 라이브러리는 넣지 않는다. 브라우저 Back과 거래 취소를 혼동하지 않는다.
- 모바일 하단 트레이는 `env(safe-area-inset-bottom)`과 실제 사용 가능 높이를 고려한다. CSS Grid/Flex로 시장·손패·보급을 배치하고 긴 ES 문구가 줄바꿈되어도 중요 카드나 확인 버튼을 가리지 않게 한다. 절대좌표는 모션 overlay의 순간적인 이동 위치에만 사용한다.

검증 gate A: KO/ES, 1440×900와 390×844, 판매 1/2/3/4/5/6/7장, 교환 2–5장, 패 가득 참, 토큰 고갈, 실패/취소를 실제 UI로 실행한다. 2장 교환은 선택 취소를 제외하면 모드 진입·카드 4장·확정의 6회 이내 활성화가 기본 기준이다. 길게 누르기·이중탭·빠른 턴 변경·실패 재시도에도 하나의 유효한 요청만 처리한다. Tab/Enter/Space만으로 모든 기본 거래를 하고 Escape 후 포커스가 사라지지 않아야 한다. 이 수치는 앞으로 사용할 기준이며 이번 측정 결과가 아니다.

### 수정 방법 B — 자이푸르의 zone과 연출 순서에만 card-game 원칙 적용

- 물리 카드 이동은 기존 `cardIds.market`, `cardIds.hands`, 공개 이벤트의 ID와 `data-jaipur-zone`을 연결한다. 게임 데이터의 상품 종류와 그림 variant를 분리한다. 판매의 앞 N장 ID가 손패 강조·비행 시작점과 같아야 하며 하나의 카드가 시장과 내 손패 양쪽에 동시에 렌더링되지 않는다.
- 현재 덱은 상품 배열, 낙타 herd는 개수이고 숨겨진 덱 ID 전체를 UI에 보낼 필요가 없다. 모든 55장에 공개 ID를 만드는 새 registry, discard/reshuffle, mana/combat/stack을 도입하지 않는다. 55장/11낙타 초기 공급과 가져오기·교환·판매 전후의 개수 보존은 현재 모델에서 검사한다. 덱 고갈 및 자동 다음 라운드는 현 계약 그대로다.
- simulation phase는 서버의 선택/대기/finished와 자동 라운드 진행이다. presentation phase는 선택/보내는 중/확정 거래 연출/정산 표시이며 서버 규칙을 기다리게 하지 않는다. view는 최신 서버 상태를 기반으로 한다. 연출 완료만 기다리다 새 상대 행동을 무시하거나 이전 state를 서버에 저장하는 일을 금지한다.
- 기존 event.sequence FIFO를 따른다: `take-single → market-refill`, `take-camels → market-refill`, `exchange`는 서로 주고받는 카드 동시 이동, `sale → bonus → round-end → round-start 또는 win`. 카드 결제와 보너스 지급은 이미 서버에서 원자적으로 결정된다. UI가 두 번째 점수계산이나 보너스 난수생성을 하지 않는다.
- 마지막 판매에서 새 라운드 토큰은 이미 0이므로 이전 라운드 동전을 새 점수로 잘못 더하는 숫자 연출을 만들지 않는다. confirmed round summary의 상품·보너스·낙타·합계에 이전 지급을 귀속시키고 현재 라운드와 분리해서 짧게 보여준다. 다음 라운드 확인 gate를 추가하지 않는다. legacy summary에 분해값이 없으면 기존 합산값만 유지한다.
- first render/remount는 최신 sequence를 기준선으로 삼아 과거 비행·효과음을 시작하지 않는다. 같은 sequence/이전 snapshot/reconnect에는 재생하지 않는다. hidden tab에서 여러 이벤트가 밀렸다면 최신 authoritative 상태로 복구하고 지난 거래 효과를 폭주 재생하지 않는다. 다음 라운드/room 전환 때 애니메이션·오디오 취소와 ID 좌표 cache 정리를 검증한다.

검증 gate B: 최대 교환의 왕복 그림, 실제 6·7장 판매의 카드 출발점, 마지막 덱 보충/자동 라운드, 한 서버 응답에 판매·보너스·정산·승리가 함께 있는 경우, viewer 변경/remount, 역순·동일 sequence를 재현한다. 버튼 submit 자체에서는 성공 효과가 0회이고 확정 이벤트에서 정확히 1회여야 한다. 상대 패/하위 토큰/미획득 보너스/덱 미래 정보는 DOM·aria·로그·정산 overlay에도 나오지 않는다.

### 수정 방법 D — 짧은 거래에 맞는 feedback와 audio mix

- small: 선택 들림/확정 전 작은 pick cue. medium: 승인된 가져오기·교환·판매의 카드 이동+도착음+해당 대상 강조. large: 실제 보너스·라운드·경기 결과의 짧은 reveal/stinger+확정된 숫자. 카드놀이에 공격게임의 화면 shake와 simulation hit-stop을 옮기지 않는다.
- 기존 WebAudio transport와 SFX gain/mute를 유지한다. UI/SFX의 개별 균형이 실제 청취에서 문제일 때만 기존 routing에 필요한 gain 노드를 추가한다. Music/Ambience/Voice와 adaptive music/sidechain은 현재 없는 기능이므로 도입하지 않는다.
- 반복 selection/card cue는 작은 재질 질감이나 제한된 pitch 차이로 피로를 줄일 수 있으나 simulation RNG를 소비하지 않는다. 소리 변화는 순수 presentation이며 보너스값/승부에 영향이 없어야 한다. volume은 기존 설정 의미를 보존하고 실제 gain과 dB 변환을 구별한다. 원래 linear gain API에 dB 숫자를 직접 넣지 않는다.
- 복수 동전·bonus·round cue가 겹쳐 master clipping을 만들지 않게 headroom과 기존 voice cap을 확인한다. cue는 AudioContext의 audio clock으로 스케줄하고 카드 도착 타이밍과 실제 스피커 출력 지연을 측정한다. mute/hidden tab/unmount 후 예약된 소리가 남지 않게 한다.

검증 gate D: 3/5/7장 판매를 반복해서 듣고 선택음·카드 도착·동전·보너스·정산의 구별/음량 균형을 확인한다. 스피커·유선 헤드폰·실제 모바일 브라우저로 확인하고, Bluetooth는 별도 출력 지연으로 기록한다. 무음과 reduced motion에서도 확정된 상품/수량/점수/라운드 결과를 텍스트로 읽을 수 있어야 한다. target timing 수치는 플레이로 조정하며 테스트 통과를 청취 승인으로 대체하지 않는다.

### 수정 방법 E — 성능은 측정 결과로만 개선

`JaipurMotion.tsx`의 layout effect는 매 렌더에서 카드/zone을 검색하고 `getBoundingClientRect()`를 읽는다. `jaipur.ts`는 legal exchange 조합을 만들어 view에 보내며 Board에서 find한다. 이는 **프로파일링 후보**이며 지금 병목으로 확인된 것은 아니다. 처음부터 pooling/atlas/새렌더러/새 action API를 넣지 않는다.

production build에서 시장5장+손패7장+최대교환+6·7장판매/bonus/자동라운드의 동일 시나리오를 Chrome Performance와 React commit trace로 기록한다. 보고할 값은 press→첫 선택 paint p50/p95, main-thread long task, layout/recalculate/paint 시간, dropped animation frames, 실제 파일 전송량/decoded bitmap 크기, 반복 경기 후 남은 timer/audio node/heap 추세다. 네트워크 ack 시간은 local paint 시간과 별도로 기록한다. 목표는 정상 환경에서 선택 p95 100ms 이내와 60fps의 16.7ms frame budget이다. GPU 비용을 직접 관찰할 수 없으면 추정치를 GPU 실측이라고 쓰지 않는다.

측정된 최고 비용 한 가지에만 수정한다. 예: layout reads가 실제 비용이면 refs/geometry 읽기를 event·resize 등 필요한 시점으로 좁히고 read/write를 분리한다. SVG filter의 paint 비용이면 동일 native-scale 이미지 품질을 유지하며 가장 비싼 filter만 단순화한다. engine 조합 또는 network payload가 실제 비용이면 legal authority/서버 검증을 유지하며 그 생성/중복전송을 먼저 줄인다. 동일 build·기기·시나리오에서 전후 값을 비교해 좋아지지 않으면 되돌린다. 카드 한 화면에 많지 않은 이 게임에 entity-game의 pool을 기본적으로 적용하지 않는다.

## 보완 후 구현 순서

기존 7개 우선순위는 유지한다. 구현은 **현 규칙/비공개정보 계약 확인 → Grid/Flex 화면 통합과 행동 트레이 → 실패·취소·단일 activation 검증 → 대표 3카드/family manifest → 기존 이벤트 FIFO와 정산 구분/음향 → 실제 두 기기·모바일·접근성 → 측정된 성능 문제 한 가지 수정** 순서다. 신규 코드가 필요한 단계마다 호출자·서버 action·legacy state·기존 unit/native fixture의 영향 범위를 먼저 확인한다. 자동 테스트/빌드, 화면 승인, 실제 Realtime, 물리 청취는 서로 다른 gate로 남긴다.

스킬 적용 보완에서는 앱 코드/자산 생성/엔진 변경을 하지 않았다. 공식 시장 페이지·규칙 원문·실기기 플레이와 실제 성능 수치는 여전히 미검증이다.

### Udaipur 코드 읽기 비교

참고 디렉터리 `/tmp/UdaipurGame`의 README는 Udaipur를 Jaipur의 온라인 클론이라고 설명하며 Seal of Excellence 타일을 없앤 것이 유일한 규칙 차이라고 주장한다. 저장소에 `LICENSE` 파일이나 package의 `license` 선언을 확인하지 못했다. 따라서 구현 코드나 그림을 복사하지 않고, 제품 행동의 비교 근거로만 읽었다.

Udaipur 화면은 왼쪽에 자원 토큰을 세로로 두고 오른쪽 위에 상대 패·시장·개별 행동 버튼, 아래에 내 손패·점수를 둔다. 시장 카드와 손패 카드를 ID로 선택하고 `takeOne`, `takeMany`, `takeCamels`, `trade`를 분리해 보낸다. 이 점은 선택 후 확정과 ID 기반 카드 추적을 확인하는 비교 사례다. 다만 그 구현은 잘못된 `takeOne`에서 선택을 지우고 경고창을 띄우며, 무효 거래는 예외적으로 선택을 남긴다. 해당 경로는 사용자 피드백이 일관되지 않아 이 구현이 복사하지 않는다. 키보드/스크린리더 동작은 코드에서 확인하지 못했다.

Udaipur `game.js`에는 `playerView: PlayerView.STRIP_SECRETS`가 주석 처리돼 있고 README TODO도 상대의 비밀 정보가 클라이언트에 전달되지 않도록 STRIP_SECRETS를 적용하라고 적혀 있다. 이는 공개 view를 분리하는 현재 엔진 계약을 유지해야 한다는 비교 근거이지, Udaipur 코드에서 재사용할 변경사항은 아니다. README의 규칙 주장만으로 공식 Jaipur와의 일치나 판매 권리를 확인한 것은 아니다.

Udaipur 코드·자산은 복사하지 않았다. 현재 KO·ES Chromium 화면/복합 조작 검사는 위 구현 검증 및 아래 Sol 검수 기록에 있다. 실제 서비스에서 동시 갱신·두 기기 재접속과 실기기 오디오 청취는 미검증이다.

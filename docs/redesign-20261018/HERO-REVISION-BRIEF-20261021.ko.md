# Hero 공간 전환 — 현재 작업 지시

상태 갱신: 2026-10-21. 이 브리프는 현재 공간 연구와 다음 검토 조건을 지정한다. 화면·모션·전체 랜딩의 합격 선언이 아니다. 상세한 이전 설계와 실패 증거는 [3b901a0 시점의 같은 문서 원문](https://github.com/da960822-ux/gitactions-main/blob/3b901a099f28a46dfa122ea9c85023010d8d2551/docs/redesign-20261018/HERO-REVISION-BRIEF-20261021.ko.md)에 보존돼 있다.

## 현재 상태와 판정

- 이 상태를 점검한 제품 커밋은 `3b901a0`; Hero 공간 비교의 제품 기준은 `5c12f9b`다.

- 새 Hero 연구는 제품에 통합되지 않았다.

- 현재 연구 산출물은 `output/current-review/hero-spatial-rework-20261021/hero-wall-volume-current/`에 있다.

- 이 브리프가 판독한 소스 SHA-256은 `7cb05eb8c4ebfc1d9595063dd03e85938f6ca71f7288d431517938fc8cd58646`이다. 이 checkpoint의 실제 정지 표본은 `.43`, `.47`, `.55`뿐이다. 같은 연구 폴더는 갱신되므로 후속 파일은 보고서의 `captureState`·source SHA·각 artifact hash가 일치하는 범위에서만 읽는다.

- 이전 캡처·후보·카메라 키는 현재 결과나 지시가 아니다.

- `.43`에서 B가 처음 보일 때 남성 인물 가장자리가 frustum 밖으로 잘린다. 짧은 부분 발견 자체를 불합격 사유로 고정하지 않는다.

- `.47`에서 두 사람은 온전히 보이지만 바깥 원경 C와 안쪽 B 사이에 실제 물체가 없는 세로 경계가 남는다. 새 석재/return 표면이 그 경계를 소유하지 않는다.

- `.55`에서는 카메라가 들어간 뒤 B가 크게 보인다. 경로와 return 깊이는 아직 해결되지 않았다.

- 따라서 현재 연구는 실패/보류다. 얼굴 보존 개선, 카메라 경로 수학, 경계 분류 또는 테스트 통과를 시각 완료로 대체하지 않는다.

- 모션·1440 독립 프레임 평가·모바일·실GPU 성능을 완료로 주장하지 않는다.

## 다음 검토 가설 — 아직 합의·구현·승인 전

root·감독·현재 owner가 다음 구조를 검토 중이다.

관측된 I의 석벽 전면에서 시작해 실제 두께를 지나 **새로 저작한 안쪽 backface 한 면**으로 이어지는 하나의 표면이 바깥 C와 안쪽 B를 나누는 후보다.

이미지 경계나 진단용 회색 return만으로 깊이를 대신하지 않는다.

이 가설의 성립 여부를 정지 화면으로 먼저 판정한다. 이를 확정된 해법이나 승인된 외관으로 취급하지 않는다.

다음 조건은 구조 후보를 검토할 때 함께 지킨다.

- 승인된 I와 B의 원본, B 도착 시 프레이밍과 인물을 보호한다.

- 승인 B의 인물·헤드셋·침대·토끼·사진의 정체성·원본 RGB를 새로 생성하거나 바꾸지 않는다. 같은 픽셀의 기하 분리와 원근 변화까지 금지하는 조건은 아니다.

- 중간 경로와 return 깊이는 고정 답으로 두지 말고, 관측 가능한 석벽·실제 가림·카메라 시야의 관계에서 설계한다.

- 보호 원본의 부족한 뒷면을 사실처럼 꾸며내지 않는다.

- 특정 힌지, 복도, 회전 방향이나 카메라 이동량을 미리 정답으로 고정하지 않는다.

제품 카메라와 공통 Host/연결은 root 소유다.

현재 Hero visual/motion/asset owner는 Sol이며, Luna는 명확한 기능 요구와 인벤토리를 맡는다.

실패 횟수에 따른 담당자 교체는 하지 않는다. owner에게 실제 프레임·측정과 잘못된 전제 또는 빠진 제약을 전달하고 같은 owner가 수정한다.

## 검수 순서와 완료 기준

1. 1920×1080과 1440×900의 실제 브라우저에서 정지 구도를 먼저 확인하고 DPR과 렌더링 환경을 명시한다.

2. 표본에는 승인 I, 출발, 첫 B 노출/공유 경계, B 도착을 포함한다. B만 보이는 도착 프레임은 전환 증거가 아니다.

3. 공유 경계에는 관측된 구조 표면의 실제 두께·가림·깊이 관계가 보여야 한다. 떠 있는 원화 사각형이나 목적 공간을 대신하는 장식은 허용하지 않는다.

4. 화면에서 보이는 방 영역, 두 얼굴/헤드셋의 가림, 도착 B 대비 추가 잘림, 원경과 B 사이의 접합을 실제 캡처에서 확인한다. 첫 발견의 자연스러운 부분 노출은 허용하되 얼굴이 잘린 채 정착하거나 오랫동안 시선을 잃지 않아야 한다. near-plane 뒤 꼭짓점의 단순 투영을 화면 점유로 보고하지 않는다.

5. 정지 구도가 성립한 뒤에만 실제 native scroll로 정방향, 역방향, 중간 반전, 직접 도착과 resize를 확인한다.

6. 구도·공간·목적·craft 각 검토 점수는 4/5 이상이고 blocking 문제가 없어야 한다.

7. 정지/모션 테스트, TypeScript, build는 각자 범위의 증거일 뿐 시각 판단을 대신하지 않는다. SwiftShader는 구도 검수 환경이며 실제 GPU 성능을 말하지 않는다.

8. 모바일은 데스크톱 구도와 모션 검수 뒤 마지막에 확인한다. 매 검수는 수정 묶음과 source hash를 연결하고 이전 실패 기록을 보존한다.

## 보호 범위와 작업 역할

Hero 작업은 다음 기능과 콘텐츠를 변경하지 않는다.

- 승인 I/B/P 원본, 첫 화면 카피와 언어 전환
- 여덟 게임, 게임 route, 갤러리 자산·팔레트·배치
- 편지 주소·제목·원문 5문단·서명
- L01–L16 발견 행동과 R01–R04 공동 기능
- API, 인증, 양측 동의, 권한, RLS와 free-tier 보호

게임/후반/갤러리 owner가 소유한 연결 계약을 보존한다. 독립 toy table/list를 기본 흐름에 넣지 않는다.

기존 Ponytail full, Impeccable craft-floor/critique, GPT Taste, Emil Animate, Three.js scene/camera 지침을 범위에 맞게 적용한다.

실제 화면·입력·접근성 증거를 디자인 검토와 연결하고, 누락된 자료를 확인한 것처럼 쓰지 않는다.

새 renderer, 라이브러리, 자산, 장식·광원으로 구조 문제를 가리지 않는다.

구조가 성립한 뒤 부족한 숨은 면의 재질·환경 자산은 필요한 범위에서 제작할 수 있다. 기존 승인 전면을 바꾸는 근거로 삼지 않는다.

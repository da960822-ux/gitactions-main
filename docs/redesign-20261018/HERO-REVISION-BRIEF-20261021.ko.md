# Hero 재수정 지시 — 승인 화면에서 역설계

2026-10-21. 상태: 역설계 정지 구도 재검수 중. 화면 합격 또는 완료 선언이 아니다.

## 현재 적용 상태

첫 수정과 2차 수정의 성공/실패는 아래 진단의 이력이다. 현재 담당자는 그대로 유지한다. 이전 제품 소스의 aperture A는 얼굴 가림과 세로 wipe 인상 때문에 불합격이며, 새 모션의 기준으로 확정하지 않았다. 정지 연구 B/C도 얼굴은 피했지만 빈 액자 같은 공간이어서 채택하지 않았다.

연구 D는 승인 B의 책상 면에서 전경 깊이를 만들었다. 최초 D의 토끼 잘림·하단 24px 미충족·책상 이음 틈은 v7의 제한된 카메라 범위와 실제 전경 면 연장으로 보완했다. 새로 드러난 원화/확장 외곽의 색 경계는 v8에서 원본 사각형 **밖의** 경계 색만 맞췄다. root는 두 해상도의 실제 v8 진입 캡처를 열어 하단 연속성과 B 대비 토끼 실루엣 보존, 새 상단 이음선 해소를 확인했다. 원본 사람/사진 픽셀을 새로 만들거나 조명을 추가한 수정이 아니다.

이는 **B와 도착 직전의 내부 구도 검수**였다. 이후 동일 담당자가 우주 전경/원경을 분리한 v11 정지 연구를 만들었고, 독립 검수는 중간 구도의 기반으로 한정해 수용했다. v6에서는 aperture A를 분리 방식의 실제 런타임으로 대체했으나 **시각 불합격**이었다. 방 노출 전 B 카메라 도착, 얼굴/토끼/사진의 B 대비 추가 잘림 방지, Hero 문구 퇴장, 첫 가시 프레임의 자산 준비는 실제 두 해상도에서 확인했다. 당시 p=.12/.14의 아치 모양 원경 접합선과 난간 잔여 조각은 남았다. 정지 연구 수용을 실제 전환 완료로 확대하지 않는다.

다음 지시는 새 힌지나 개구부 형태가 아니라 **승인 원화의 중요 오브젝트 보존·화면 점유·연속된 면**을 조건으로 삼는다. 카메라·크기는 v6 상태로 고정한다. 현재 측정상 원경 원본/생성본의 전역 이동은 약 1 source px지만 경계 부근 색 차이는 평균 약 18/255라 UV 이동만으로 해결되지 않는다. 원래 돌/난간 색을 다시 섞어 접합을 숨기지 않는다. 움직이는 가까운 물체의 불투명 표면은 끊기지 않아야 하고, 옛 물체 조각이 먼 배경에 남아서는 안 된다.

**총괄 지시 정정:** 전환 내내 모든 원경 픽셀까지 고정하라는 조건은 사용자의 직접 요구가 아니라 총괄이 추가한 구현 제약이었다. 이 때문에 다른 두 배경을 소품 윤곽에서 붙이는 접합 문제가 커졌다. 원본 p0와 승인 B·인물을 보존하면서 초기의 먼 배경만 일관된 cleanplate C로 이어 주는 후보를 다음에 확인한다. 실제 전경 기하·표면·카메라 이동은 유지하므로 전체 전환을 페이드로 대체하는 지시가 아니다. root와 독립 검수자는 두 자산을 직접 비교해 이 제한적 변경의 타당성을 확인했으나, 아직 실제 화면의 성공은 아니다. C의 구름·행성 명암·도시 세부가 달라 긴 혼합은 이중 풍경이나 이유 없는 하늘 변화로 보일 수 있다. p=.08/.09/.10/.12/.14/.16 및 p0/B를 두 해상도에서 실제 확인하고, 배경 교체 자체가 드러나면 다시 실패로 기록한다. 추출 마스크의 꽃/소품 경계 결함은 별도로 남을 수 있다. 이 정지 경계 검수 전 전체 모션은 통과시키지 않는다. 카메라 각도의 극적인 변화는 필수가 아니다. 2.5D 원화/전경 투영을 완전한 3D 실내 재구축이라고 부르지 않는다.

## 현재 v8 실제 화면 확인

root는 1920의 p=.09/.12/.14 및 1440의 p=.16 실제 브라우저 PNG를 열었다. 일관된 원경 handoff 뒤 아치 모양 색 패치와 먼 배경에 남던 난간/천구 흔적은 해소됐다. 중간의 방 점유와 두 얼굴·토끼 보존도 유지됐다. 다만 움직이는 근경 장미·잎의 추출 가장자리와 작은 잘못된 투명 영역은 남아 **전체 시각 합격이 아니다**. 이후 1920×1080 backing DPR1의 p=.14/.16도 root/담당자가 실제 열어 같은 추출 오류를 확인했다. 단순 저해상도 확대 현상이 아니다. 제한된 ES 실제 입력 검사에서는 두 해상도의 포인터 반응/분리 전 정착, 중간 반전·resize 복귀의 같은 행렬과 p=.12 캡처 일치, 도착 전경 퇴장·가로 overflow 없음이 확인됐다. 첫 자동 비교 불일치는 ScrollTrigger refresh/scrub 정착 전 검사기 측정 때문이었고 제품 좌표를 변경하지 않고 검사기를 정정했다. 추가 기술 mask 후보3은 원래 벽을 다시 투명화하고 소품 안쪽 검은 선을 만들었으므로 root가 거절했으며 제품에 연결하지 않았다. 새 장식/조명/원화 인물은 생성하지 않았다.

최신 v8 검사는 관련 3개 파일/27개 테스트와 production TypeScript·Vite·edge build를 통과했다. 원시 로그는 `output/current-review/hero-spatial-rework-20261021/runtime-separated-v8/final-checks.log`다. 이전 v6 전체 77개 파일/616개 성공과 구분한다. [ES 실제 브라우저 Hero→B→중간 복귀 영상](evidence/hero-room-v8-es-1x.mp4)은 8.52초·1배속·960×540 출력·자막 없음이다. 전체 랜딩 완성 영상이 아니며 SwiftShader 녹화의 25fps 파일 규격을 실제 GPU 성능으로 해석하지 않는다.

## 이전 지시의 문제

정지 D의 독립 검수도 같은 결론이다. B 원본에서 이미 화면 오른쪽에 닿는 토끼 실루엣은 원본의 구도이며, 진입하면서 **B보다 더 잘리는 것**이 수정 대상이다. 존재하지 않는 원본 바깥을 새로 그리라는 지시가 아니다. 중앙 분홍 구분선도 승인 원화 일부다. 그 아래 새로 드러난 검은 틈만 기하 결함으로 구분한다. ‘잘림 없음’ 같은 뭉뚱그린 조건 대신 원본 대비 악화와 새 표면 경계를 측정해야 한다.

첫 지시는 수평 분할 제거를 성공으로 삼고, 담당자가 원인을 측정하기 전에 총괄이 측면 힌지를 해결책으로 제시했다. 방 카메라 추종을 제거하면 생기는 목적 방의 투영 면적과 빈 여백까지 같은 설계로 해결하도록 요구하지 않았다. 고정 방 행렬·불투명 인물·연속 mesh·테스트 성공이 화면 구성을 대신했다. 결과적으로 수평 분할은 사라졌지만 p=.20–.24의 검은 여백 속 사각 원화와 p=.18의 얼굴 잘림으로 바뀌었다.

첫 Hero/B 도착 픽셀 일치만으로 중간 구도에 합격을 줄 수 없다. 특정 축의 회전·힌지·기존 이동 거리·계속 늘려 온 버전 구조를 다음 작업의 전제로 두지 않는다. 모델 변경이나 조명 추가를 해법으로 삼지 않는다.

## 담당자에게 전달할 새 프롬프트

당신의 일은 승인된 풍성한 우주 첫 화면과 B 게임방 사이의 **완성된 중간 구도**를 설계하고 실제 브라우저에서 구현하는 것이다. 이전 수정 코드의 운동 방식을 유지할 의무는 없다. 게임·편지·게시판·원격 이벤트·후반 소스는 건드리지 않는다. 카메라/공유 공간은 당신만 소유한다.

1. 활성 import 경로부터 확인한다. 진단 문자열·계획상의 사용 도구·로드 성공은 화면 증거가 아니다. B 원화는 rigid illustration이며 실제 내부 방 메시가 아니다. 이 한계를 숨기지 말고, 고품질 원화와 필요한 실제 3D 표면/카메라를 함께 사용한다. 모든 소품을 3D로 만드는 것이 목표가 아니다.
2. p0와 승인 B의 기존 화면은 보호한다. faces/outfits/headsets/bed/rabbit/photo와 원화 픽셀을 새로 생성하거나 변형하지 않는다. 기존 gallery/palette와 원문은 그대로 둔다. 이미 승인된 B를 다시 사용자에게 승인받는 절차를 만들지 않는다.
3. 좌표부터 고치지 말고 첫 화면·초기 이행·주요 중간·방 노출 완료·B 도착의 구도를 정한다. 각 상태에서 카메라 frustum, 보이는 방 원화 경계, 원화 투영 사각, 두 얼굴의 안전 영역과 떠나는 문구의 영역을 계산/기록한다. 중간 화면 한 장에 떠 있는 사각 사진·큰 빈 여백·잘린 주인공이 있으면 그 구도부터 다시 설계한다.
4. 방이 드러나는 opening 안은 목적 방/그 공간으로 채워져야 한다. Hero 표면이 떠난 뒤 방 원화의 사각 경계와 검은 gutter가 노출되면 불합격이다. 방 노출 전에 관찰 거리를 맞추는 짧은 카메라 경로와 전경 stage의 공간 비율을 함께 설계한다. 먼 곳의 작은 원화를 억지로 크게 만드는 임시 billboard/scale 분기로 해결하지 않는다. 필요하면 Hero 전경 stage 자체의 물리 위치·단위를 재설계해 **가까운 B 카메라와 양립하는 초기 구도**를 만든다. 원화 관통이나 긴 복도는 쓰지 않는다.
5. 인물은 주인공이다. 카메라 접근으로 갑자기 커지거나 여자친구 얼굴이 화면 밖으로 잘리지 않게 한다. 떠나는 과정은 의도된 가림/공간 이동으로 읽혀야 하며, 화면 경계에서 반쪽 얼굴이 남는 상태를 합격시키지 않는다. DOM 카피도 목적 방 위로 잘려 흘러가지 않도록 별도의 안전 영역/종료 시점을 갖는다.
6. 실제 3D 표면의 법선 변화·원근과 필요한 카메라 이동은 유지하되, 회전 축·힌지 방향·이동 거리는 해법이 아니다. 단순 fade/slide 또는 동영상만으로 공간 전환 완료를 주장하지 않는다. 승인 원화의 입체 재구축을 하지 않았다면 그렇게 표시한다.
7. 정지 구도가 먼저다. 1920×1080 및 1440×900에서 전/중/후 실제 browser capture를 확보하고 root에게 즉시 경로를 전달한다. 새 장식·광원·장미·거대 소품·배경색 교체·추가 이미지 생성은 이 문제를 해결하는 수단으로 쓰지 않는다. 원본과 같은 언어/논리 viewport로 비교한다. 낮은 backing DPR/SwiftShader는 구도 검사용이라고 표시한다.
8. 정지 구도가 확보되면 같은 진행값의 정방향·역방향·중간 반전과 resize/직접 도착을 확인한다. GSAP scrub이 아직 정착하지 않은 값의 비교는 별도로 기록하고 pure pose 테스트를 실제 모션 합격과 혼동하지 않는다. 테스트/TypeScript/build/스크린샷을 각각 해당 범위로 보고한다.
9. 검수는 구현·수정 묶음마다 제한된 횟수로 수행해 무한 미세 패치를 피한다. 결과가 실패하면 구체 측정과 원인을 제출한다. 총괄은 실패 판정만 전달하지 말고 프롬프트의 잘못된 전제/빠진 제약을 수정한다. **사용자 최신 지시로 실패 횟수에 따른 자동 담당자 변경은 폐기했다.** 현재 담당자가 개선된 지시와 구도로 재설계하고 같은 조건에서 확인한다. 후반 공유 연결부는 이번에 확정하지 않는다. 모바일은 마지막이다.

## 확인할 도구와 자산

Ponytail full, 실제 설치된 Impeccable craft-floor/critique, GPT Taste, Emil animate를 범위에 맞게 읽고 어떤 결정에 적용했는지 남긴다. 누락된 참조를 읽었다고 하지 않는다. 새 라이브러리는 설치하지 않는다. HyperFrames/Remotion 자산은 별도 인벤토리 중이며 사용은 실제 화면 기여가 증명될 때만 보고한다. 발광 강도0 같은 죽은 연결을 고쳤다는 이유만으로 승인되지 않은 과거 영상/미술을 다시 노출하지 않는다.

# Da Vinci table

The Da Vinci Code table uses a charcoal felt surface with contrasting ivory and black ceramic-style tiles. In the 26-tile ruleset, each color has values 0–11 plus one joker; the joker appears as a full-width dash. Setup lets each player privately place any starting joker in one of the legal gaps, then confirm readiness. A later drawn joker uses the same gap selector. Older 24-tile rooms keep their twelve-number selector. Each tile keeps its public color and sorted position visible; only the owning player and already-revealed tiles show a value. The opponent rack uses positional keys, so private values never become DOM identifiers.

The active player can select a hidden rival tile directly, filter the rack by its visible color, and choose a value from the legal 0–11 / joker selector. The component enables a guess only when the current player view includes that exact legal action. A confirmation step repeats the selected target and value before sending the unchanged engine action. The public phase strip also shows remaining deck count and turn count; each seat's rack and the labeled count of hidden rival values are visible.

Motion follows authoritative snapshots. A new untouched setup deals its current rack with a short stagger; confirming or reloading a later state does not replay that deal. A draw marks the new tile, joker placement animates only the arranged owner tile when its public insertion position matches, a correct guess flips the target that was publicly revealed, and a wrong guess flips the acting player's newly drawn tile when the public event provides its index. Stop, draw-skip, turn, and result messages describe the actual transition. The first mounted view does not generate an action event, event state is scoped to the viewer, and brief feedback timers are cleaned up on replacement or unmount. Reduced-motion settings disable transitions and animation.

The component plays the local selection cue when the player picks a tile or number. Guess-attempt tension and confirmed draw, reveal, turn, and result cues are owned by the shared action/event audio layer, avoiding duplicate sounds in the table. Sound remains subject to the shared gesture unlock and per-game preference.

The user-requested 26-tile ruleset adds joker placement and initial readiness actions; numeric sorting and correct/wrong/stop behavior remain unchanged. Once placed, a joker cannot be repositioned. Recent history shows only the public target position and attempted value, and the visual feedback uses the engine's public `lastEvent` / `actionLog` when available. A snapshot comparison fallback supports older states without event metadata. No opponent secret value, seed, or deck contents are read from the view.

Focused checks in `src/app/DaVinciTable.test.tsx` cover malformed hidden-value privacy, both locales, legal target/value controls, explicit joker action matching, private setup placement gaps, readiness action, publicly revealed values and guesses, viewer isolation, and the distinct wrong-guess target versus revealed-tile positions. Run with `npx vitest run src/app/DaVinciTable.test.tsx`; TypeScript validation uses `npx tsc -b --pretty false`.

The default includes jokers at the user's request. Published rulebooks call this the advanced variant; this app offers one default ruleset, not an additional mode switch. Placement events are retained for their owner only, so the other seat's event log does not identify a hidden joker's exact position. Visible color and ordering still provide legitimate deduction clues.

Replay uses the existing request-and-consent flow. Match records count only results observed during the current mounted browser session; they are not permanent account statistics. Browser integration checks run against the local SQL/RLS HTTP fixture. That fixture has no Realtime service, so peer refreshes are explicit and production push synchronization remains unverified.

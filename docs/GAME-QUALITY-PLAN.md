# 세 게임 품질 개선 제안

기준 소스: da960822-ux/gitactions-main, origin/main 59d1047.
범위: 도미노·자이푸르·스플렌더 각각 별도 서브에이전트 감사. 아래 제안은 구현 전 계획이며, 현재 구현 상태는 [구현 기록](GAME-QUALITY-IMPLEMENTATION.md)과 [재검수](GAME-READINESS-RECHECK.md)를 기준으로 확인한다.

## 근거와 한계

최신 소스, 게임별 구현 계약, SESSION-HANDOFF, QUALITY-VISUAL-AUDIT를 읽었다. 화면 높이 수치는 저장소에 보관된 2026-10-11 초기 상태 감사 결과이며 이번에 재측정한 값이 아니다. 경쟁작 공식 사이트 요청은 네트워크 정책에 의해 차단됐다. 경쟁작 최신 UI를 직접 플레이하거나 현재 조작·음향을 실측했다고 주장하지 않는다.

외부 비교 후보: Flyclops Domino!, Board Game Arena의 Jaipur와 Splendor, Space Cowboys의 해당 게임 규칙. 모방할 화면이 아니라 행동의 명료성, 공개 정보, 확실한 입력 반응을 평가하는 기준으로 삼는다.

## 공통 선행 작업

1. PlayApp 방 헤더의 제목·상태·초대·메뉴를 작은 공통 바에 통합한다. 게임별 공개판, 내 패, 주요 행동이 1440×900 한국어/스페인어에서 동시에 보이도록 구성한다. 도움말·상세 기록만 별도 펼침 영역에 둔다.
2. 즉시 입력 피드백과 서버가 확정한 결과를 구분한다. 선택은 바로 반응하고, 전송 중에는 선택 대상과 진행 상태를 보여주며, 성공 연출은 확정 상태 이후에만 재생한다. 실패 시 선택을 보존하고 원인을 안내한다.
3. core/client.ts에 연결 중/연결됨/끊김/복구 상태를 반영하고 실제 재동기화 경로를 만든다. 현재 subscribe 콜백은 SUBSCRIBED만 처리하며, PlayApp의 snapshot.error 재시도는 getSnapshot을 다시 읽을 뿐 새 요청을 보내지 않는다. 기존 요청 ID, 버전 검사, 중복 방지 및 방 전환 보호를 유지한다.
4. 이미 있는 이벤트·모션·오디오 시스템을 재사용한다. 실제 물체의 출발·도착 위치와 소리 시점을 맞춘다. 새로고침/재접속은 과거 효과를 재생하지 않는다. 감소된 모션 설정, 키보드 조작, 색 외 정보와 음소거를 유지한다.

## 도미노

- 기존 SVG 28종, 합법 타일/끝 선택, 팀 규칙 및 확인 이벤트 효과를 유지한다.
- 현재 긴 가로 체인과 수직 정보 패널 때문에 양끝과 손패를 동시에 보기 어렵다. 팀/좌석 배지를 테이블 둘레에 통합하고 설정은 준비 단계 이후 접는다. 감사의 한국어 보드 높이는 1172px이다.
- 대표 조작은 손패 선택 → 합법 끝의 배치 미리보기 → 원하는 끝 확인 → 확정 후 해당 끝으로 이동이다. 드래그는 추가 입력 방식이며 클릭/키보드를 대체하지 않는다. 불가능한 끝은 이유를 표시하고 전송 실패는 선택을 남긴다.
- 긴 체인은 읽을 수 있는 최소 타일 크기로 테이블 안에서 이어지게 배치한다. 전체 체인을 임의로 축소하지 않고 양끝 접근과 최신 타일 식별을 보장한다.
- 손패 원점부터 도착 끝까지 이동시키고 타일 정착에 맞춰 착지음을 낸다. 패스·막힘·보너스·라운드 정산은 실제 이벤트와 팀 기준으로 간결하게 보여준다. 상대 패는 공개 카운트와 뒷면만 사용한다.

## 자이푸르

- 기존 55장 엔진, 안정된 카드 ID, SVG 상품, 모션, 모바일 접근과 정산 내역을 재사용한다.
- 230px 시장 카드와 여러 패널로 손패·토큰 공급이 아래로 밀린다. 감사의 한국어 보드 높이1224px, 손패 시작 y863이다. 시장/손패 두 줄과 옆 상품 토큰 레일로 재구성한다.
- 현재 손패 클릭은 교환 모드에서만 가능하고 판매는 상품×수량 버튼을 따로 나열한다. 손패로 판매할 묶음을 직접 고르고 한 행동 트레이에서 상품 점수와 보너스 유무, 확인·취소를 표시한다. 비공개 보너스의 실제 값은 공개되기 전에 노출하지 않는다.
- 교환은 시장/손패 선택을 나란히 표시하고 2/3처럼 수량의 불일치를 알려준다. 미완성 선택으로 전송하지 않고 실패 시 선택을 보존한다.
- 상품 카드의 그림·배경·테두리·수량 표기를 한 시스템으로 통일한다. 판매 카드 → 상품 토큰 → 공개된 보너스 → 점수 도착 순서로 기존 모션을 다듬는다.
- 현재 낙타 교환, 다음 라운드 선공, 동점 처리 등에는 보존해야 하는 자체 규칙 계약이 있다. 공식 규칙 대비 차이를 명시하고 공식판 일치를 별도 결정하기 전까지 엔진을 임의로 바꾸지 않는다.

## 스플렌더

- 기존90개 카드/10개 귀족, 이미지와 엔진의 대응, 구매/예약/토큰 효과와 비공개 예약 보호를 유지한다.
- 카드마다 조작 영역을 상시 붙여 3단 시장과 내 토큰이 동시에 보이지 않는다. 감사의 한국어 보드 높이는1546px이다. 3×4 시장, 귀족, 은행, 내 토큰/예약을 한 화면에 구성하고 선택한 카드에만 행동 패널을 연다.
- 대표 구매는 카드 선택 → 비용/영구 할인/지불 토큰/부족 자원 확인 → 구매 확정이다. 구매 불가 카드도 비용을 확인할 수 있어야 한다. 작은 그림 속 숫자만으로 설명하지 않고 엔진 데이터 기반 가독성 표시를 제공한다.
- 보석 선택과 10개 상한에 따른 반환을 하나의 계획으로 시각화한다. 현재 조합별 반환 select 대신 토큰을 직접 선택하는 UI로 개선하되 최종 행동은 기존 legalActions와 정확히 일치시킨다.
- view에 있는 상대의 공개 보너스를 보여준다. 상대 색별 토큰은 현재 엔진/테스트에서 숨기는 정책이므로 공식 공개 정보 설계와의 차이를 검토한 후 계약을 바꾼다. 예약 얼굴·덱·seed·전체 비공개 상태를 노출하지 않는다.
- 보석 스택과 기존 카드 아트의 재질을 통일하고 보석 이동·카드 획득·귀족 방문·마지막 턴을 실제 결과에 맞춰 연결한다.
- docs/ASSETS.md는 카드 그림에 대한 독립적인 출판사 허가를 확인하지 못했다고 명시한다. 현재90+10그림 유지 요구는 보존하되 실제 유료 배포 전에 권리 확인 또는 사용자와 합의한 원본 아트 교체가 필요하다.

## 구현 순서와 합격 기준

순서: 공통 화면/연결 처리 → 각 게임 대표 행동 하나 완성 → 복합/종료 상태 → 자산/모션/음향 마감 → 실제 두 기기 회귀 검증.

- 1440×900 KO/ES에서 기본 및 복잡 행동의 공개판·손패·핵심 조작을 스크롤 없이 수행한다. 자이푸르는 기존 모바일390×844 흐름도 유지한다.
- 입력 선택은 즉시 눈에 보이도록 하고 100ms 이내 시각 반응을 목표로 측정한다. 이는 서버 확정시간 보장이나 현재 측정값이 아니다.
- 긴 체인, 묶음 판매, 최대 교환, 토큰 반환, 다중 귀족, 마지막 턴/라운드 정산을 실제 UI에서 검증한다.
- 서로 다른 두 로그인/기기에서 정상 전체 경기와 지연·중복 입력·연결 끊김·재접속을 확인한다. 로컬 fixture 통과를 실제 Realtime 검증으로 대체하지 않는다.
- 확인되지 않은 성공 모션/효과음, 중복 정산, 재접속 후 과거 효과, 상대 비공개 정보 노출이 없어야 한다.
- 키보드, 포커스, 감소된 모션, KO/ES 긴 문구, 실제 음향 청취를 확인한다. 기존 엔진/UI 테스트와 빌드는 회귀 검증이며 시각적 완성도 자체의 승인과 구분한다.

이 문서는 구현 전 개선안과 기준을 보존한다. 이번 구현 결과와 실제 검증·남은 출시 관문은 [구현 기록](GAME-QUALITY-IMPLEMENTATION.md)에 있다. 상업 출시 준비 완료를 뜻하지 않는다. 유료 매칭·랭킹·새 게임·운영 배포는 추가하지 않는다.

### 행동과 연출의 공통 계약

대표 행동마다 `대기 → 선택/미리보기 → 전송 중 → 확정 결과 또는 실패`를 명확히 한다. 모달/도움말은 포커스를 소유하지만 온라인 상대의 턴 진행을 멈추지 않는다. 전송중과 장식모션중은 다른 상태이며, 장식이 끝나지 않았다는 이유로 합법적인 다음행동을 막지 않는다. 오래된선택은 같은index의다른물체로 전송하지 않고 무효화하거나 최신legalAction에 정확히재매핑한다. 실패에서는 아직유효한선택을보존하고, 처리여부가불명확한경우 최신상태를확인한뒤 새행동을허용한다.

| 중요도 | 표시·음향 시작점 | 세 게임의 예 | 확인 조건 |
| --- | --- | --- | --- |
| 작음 | 로컬선택즉시, 짧은lift/윤곽과작은select음; 약120ms 초기값 | 타일/상품/카드 선택, 토큰 임시선택 | 자원/소유권/점수는 변경하지 않는다. 색외선택표시가 있고 무음에서도 이해된다. |
| 중간 | 확정된 물체 이동과 짧은착지음; 약240ms 초기값 | 타일놓기, 시장가져오기/교환, 보석이동/카드구매 | source→target·actor·물체identity가 실제공개결과와일치. 실패요청에는 성공연출0회. |

### 수정후 검증 방법과 종료 조건

1. 수정전 대표행동을production build에서기록한다. 기본/최대물체수/복합정산의입력→선택표시, 서버확정시간, frame/paint spike, 이미지decode와실제음향을분리한다.
2. 화면/행동단위로구현하고 기존관련테스트에 실패할수있는회귀를보강한다. 단순스타일수정에구현을그대로반복하는테스트는추가하지않는다.
3. 동일기기/시나리오로수정전후를비교한다.100ms이내로컬선택표시,60Hz16.67ms frame budget은측정목표이며 모든기기의보장이아니다. 지속적인초과가있으면원인을측정해가장큰비용부터수정한다.
4. KO/ES1440×900,125%확대, 실제지원최소폭, 자이푸르390×844/실제모바일에서기본/복잡행동을수행한다. 스플렌더/도미노의현재desktop지원범위를임의확대하지않는다.
5. 실제Supabase두사용자/두기기정상전체경기,느린응답,오프라인,응답유실,중복입력,재접속,방전환을검증한다. fixture/manualrefresh는별도결과로남긴다.
6. 대표시안과실제playcapture, 물리음향, 기본/복잡/종료상태를확인한뒤완성여부를판정한다. 테스트/빌드/이미지생성통과는사용감승인의대체가아니다.

구현 전 계획 단계에서는 스킬 설치·75파일 validation·upstream SHA-256 확인·기획 보완만 완료돼 있었다. 이후 세 게임 UI·조작·아트·연결 복구·그림 설명을 구현하고 운영 빌드 대표 행동을 검수했다. 모든 계획 항목이 같은 방식으로 구현된 것은 아니며, 드래그 입력·전체 경기 성능 전후 비교·실제 Supabase/물리기기 검증은 완료로 표시하지 않는다. 현재 항목별 구현·대체 방식·미검증 상태는 [재검수](GAME-READINESS-RECHECK.md)에 기록한다. 원격 push/공개 배포는 수행하지 않았다.
